# 项目长期约定（Miruku 项目）

> 本文件是 WorkBuddy 的个人笔记，**不是事实来源**。现行进度看 `WORK_LOG.md` 顶部「当前状态」；缺陷状态看 `docs/defect-register.md`；已拍板的决定看 `docs/otto-decisions-20261024.md`。本文件里的结论可能已被后来的实测推翻。

## 协作规则（与 Codex、DeepSeek 三方同步）

- 项目根目录有 `WORK_LOG.md` 留言板，是 WorkBuddy 助手、Codex、DeepSeek 三方唯一的同步点。
- **每次开工前先读 `WORK_LOG.md`**，了解其他人推进到哪、待办、已拍板决策。
- **每次完成实质工作后，在 `WORK_LOG.md` 顶部追加一条进展**（日期/谁做的/做了什么/影响了什么/下一步），只追加不删历史。
- 不覆盖、不推翻已拍板的决策；冲突时先读记录、留言说明，不直接覆盖。
- 三方分工：Codex=工程侧（脚本/插件/自启动/数据库）、WorkBuddy=产品体验侧（人设/口吻/情绪边界/文档）、
  DeepSeek=模型内容侧（最终回复生成）。DeepSeek 交接见 `docs/handoff-deepseek.md`。

## 已拍板的核心决策（不推翻，除非 OTTO 明确改）

1. 最终只服务那一个人（QQ 10000002），宁肯过度设计也不愿出岔子——不砍复杂度。
2. 方向是「陪伴」而非「分析/让对方变好」。对方情绪袒露极稀少，Miruku 做的是「识别并接住袒露」，不主动挖掘、不追问、不贴标签。
3. 成功度量未定，先落地最小原始字段记录（会话消息数/回复间隔/危机·低落触发标记）。
4. 稳定性 vs 优化 的优先级交由 Codex 判断并说明理由。

## 技术铁律

- 不重写 AstrBot 消息管线，不自己造主动调度器。
- 所有脚本只能在 AstrBot Launcher 实例的 Python 环境跑（系统 Python 缺 jwt/psutil）。
- 不打印任何 API Key 或 jwt_secret。
- 权威文件：`docs/handoff.md`、`prompts/system.txt`、`persona/emotional_cues.md`。
- **断言机制行为前必须贴源码行号。** 已三次犯错（"必须停机"、"调度器不排期"、"判据写绝对"），根因都是从语义直跳实现。
- 参数值只从运行配置（`GET /api/v1/system-config`、`/plugins/config`）或运行 JSON 读，**不从 `default.py` 抄**（曾把出厂默认当实测值，错 4 处）。
- 主动消息插件调度链路（`astrbot_plugin_proactive_chat`）：`flow_orchestrator.py` 发送后**无条件**排下一任务 → `gating_feature.py` 按 `max_unanswered_times` 拦成 `STOP` → 重启由 `scheduler_service.py` 恢复/初始化（有效期 `next_trigger+60s`，超时则不创建触发器）。任何"例外"要生效必须同时改前两处。
- **送达判定不得合并层级**：`send_proactive_message` 是"任一段成功即整体成功"，成功后才计数并写全文历史；观察插件每"一次主动消息"只记 1 行（派发在分段循环之后）。**QQ 气泡数才是唯一送达证据**，行数与记录都不算。
- **`enable_auto_trigger=false`（实测）**：停机跨过 `next_trigger+60s` 后主动消息**静默停摆**，只有来世本人发言才会重排。涉及恢复/重连的任何设计都要考虑这条。
- **写文件不能替对方刷新上下文。** Codex / DeepSeek 是独立窗口，读的是**开始那一刻的快照**。发现「我写了但他没看到」时，别重写内容：① 把入口放到对方**第一个会读的位置**（`WORK_LOG` 状态区顶部、任务单顶部索引、`handoff.md` 必读清单）；② 明确告诉 OTTO 说一句「重读文件」；③ 在文件里写明「若你没有这条＝上下文过期，请重读，别凭记忆」。本项目实测：派单内容写全了（56 行正文＋两处摘要），但 `handoff.md` 零处提到任务单、`## Codex 同期任务与接力规则` 是个空标题 → 对方压根找不到。**同一文件内也有位置问题**：git 建仓记录写进了 `WORK_LOG` 状态区和最新进展两处、也进了提交，但被后一条同型条目压在下面、且关键词落在长条目的中段，OTTO 照样读成"你没写"。所以「写进去了」和「能被看到」是两件事——**新事实先进状态区第一条，别压在同型条目下面；同一件事只留一条，重复摘要会让人以为是两件事。**
- **文档内部互相引用不写死行号，一律按标题搜索定位。** 同一文件里插一段索引，后面的行号全部漂（实测 `## L1` 405→437，索引当场过期）。行号只在「引用源码断言」时写，且写完立刻回读核对。
- **跨文档引用规范时必须回读那一条原文，不能凭记忆写「见 §X」。** 已被 Codex 连续退回 5 次（WB-03、03R、05、05R、06），其中 WB-06 是我自己写的两份文档互相矛盾（WB-05R §3.1 定 T0=首段出站，WB-06 §六-5 却用 `all_segments_accepted`）。
- **告警三个语义不许混**：`suppressed_push_count` 只数"因限流未推送"；传输失败走 `delivery.failed_reason`（`transport`/`target_check`）；`push_state = failed_final` 是终态（`crisis-alert.md` v4/v5），调度器扫到必须跳过，且与 `resend_state = active` 互斥。
- **告警有两个时钟，入口只判 `first_pushed_at`**（`crisis-alert.md` §7.9，v5）：`= null` 走**传输重试**（`transport_retry.next_retry_at`，退避 60s→1h 封顶，不放弃，`resend_count` 恒 0，`resend_state = none`）；`≠ null` 才走**三次提醒补发**（+15/+30/+45 从 `first_pushed_at` 起算）。**"首次成功前的重试"不是"补发"**，写成一件就会出现"断线 2 小时恢复后，系统报告已补发 3 次、OTTO 只收到 1 条"。
- **凡是"到期就发"的调度，必须在每次尝试前先把下次时间写盘推进到未来再发**。否则崩溃+重启会对着一个"已到期的过去时刻"无限狂发。加字段不够，必须写消费侧行为。
- **故障的诚实标准按收件人分**：对来世，失败就当没发生（不补发、不道歉、不提延迟）；对 OTTO，失败必须留痕（停摆要显式、告警要重试）。同一套基础设施，两套标准。
- **验收例不许要求"在生产环境做破坏性操作来亲眼验证"。** 被 Codex 连退两次（WB-08 v2 的"移出白名单"、v3 的"清空白名单"）。正确做法：① 只读源码断言（代码顺序就是行为，`39 < 71` 这种位置关系本身即结论）；② 隔离单测（用**真实**方法 + 内存假对象，不读也不改运行配置）。样本：`data/probe_whitelist_empty.py`（10/10）。写操作卡前先问一句「这一步失败时，会不会把不该放进来的人放进来」。
- **凡是"连续 / 不间断 / 稳定运行"的门槛，必须先回答「心跳写在哪一行」。** 没有周期心跳的系统，**进程死 / QQ 掉 / 插件崩三种故障在数据上完全同形——都是"什么都没有"**，于是"看起来正常"等于"什么都没发生"。本项目实测：11 个启动段中 9 段从未连上 QQ，历史最长连续段 6h10m，而期间所有文档都写着"链路已验收"。判据必须由可复跑探针算（`data/probe_uptime.py`：一次 `core.main:144` ＝ 一次启动；段内出现 `aiocqhttp_platform_adapter:107` 只证明**连上过**——它是链路事件，**不是**在线证明），**不许靠回忆"我记得没关过"**；重启一次＝计时归零，不许累计，不许"这次不算"。
- **「连续运行」门槛还要先回答第二个问题：「跑在哪台设备上」。** 换载体＝重装＋重扫码＋探针路径全改，旧载体上跑够的时间**一律不作数**。所以**先定载体，再开始计时**，顺序反了就是白跑一遍。载体判断第一条看它**是不是他的主力机**——主力机（手机尤其）在他使用期间必被切后台，而且被杀时零日志，等于回到"三种故障同形"。长期插电高负载还有电池鼓包风险。
- **上云的真实风险是 QQ 号，不是钱。** 机房 IP 登 QQ 触发风控是常态（典型 **168「账号近期存在安全风险」**），解除**只能机主本人在最新版手机 QQ 做人脸/短信验证**；容器重建还会被识别为新设备。所以：号不是他本人注册的 → 机房 IP 基本不能碰；是他本人的 → 也必须**先在电脑（家宽）养熟再迁**，迁移一次到位，之后不换 IP、不重建容器。**教程里的 CentOS 7.x 已 EOL（glibc 太老跑不了 Electron），1核2G 会被 AstrBot+LinuxQQ 顶到上限**——这两条照抄必卡死。
- **事件 ≠ 心跳：给"持续性"写判据前，先问一句「这个数变大，是变好还是变坏」。** 第一版把 `适配器已连接` 当在线证据，结果**重连越频繁、证据越密、越容易判达成**——方向整个反了。正确做法：把**链路事件**（只证明某一刻发生，重复出现即中断）与**心跳**（周期性、证明此刻仍在）分成两类，前者 ≥2 次直接判 `BROKEN` 归零。配套两条：① 判据要有"结构上不可达"的档位（`HEARTBEAT_MARKS = ()` → `PROVEN` 不可达，与日志内容无关），这样"缺心跳"不会被任何日志内容掩盖；② 自测**必须同时有正反两侧样例**（重连不得产生 `PROVEN` ＋ 注入真心跳必须能到 `PROVEN`），否则"永远给不出通过"和"什么都能通过"看起来一模一样。
- **自建任何通用能力前，先查框架内置有没有**，而且查的顺序比结论重要：① **有没有**（`grep -rn --include=*.py`，别看文档看代码）；② **硬前提是什么**；③ **数据形态合不合**。本项目教训：我们写了 548 条 + 手写词法打分 + 注入钩子，而 AstrBot v4 自带 `knowledge_base/`（1890 行，faiss 向量 + rank-bm25 + RRF，注入点 `astr_main_agent.py:1879` 现成）。但只查第 ① 条就换方案同样是错的——内置硬卡在 `kb_mgr.py:101–102` 强制 `embedding_provider_id`，而实例零 embedding → 等于**每轮一次外部调用、给"不间断"门槛新增一个故障源**。**三条都过才用内置；只查一条就换，是用一个没看清的坑换掉另一个。**
- **复用"现成能力"前，先确认它补的是哪个方向。** 名字对得上不代表覆盖得到：观察插件有"补历史"逻辑，看起来正好能补"进程中断期间漏掉的消息"，但它读的是 AstrBot 自己写的库、且只取 `sender_id='bot'`——**补的是"她自己发过的"，永远补不出"她没收到的"**（`astrbot_plugin_miruku_observer/main.py:42`）。配套两点：① **"能不能测"与"跑起来要不要接口"必须分开**——判定一条消息有没有丢，用眼睛看客户端就够，不必等接口；② 兜底类断言写成**"不许不知道"**而不是"不许丢"（丢不丢由协议层决定，知不知情才是我们能守的），且"不知道"必须被明确列为**不可接受答案**，否则它总是默认通过。
- **改 `persona/*.md` 不会改变她的任何行为。** 运行人格只有 `prompts/system.txt`：`deploy_miruku.py:13` 读它、`:21` 整段 PUT 成 `persona_id=miruku` 的 `system_prompt`（`begin_dialogs: []`）；实例目录 `grep -rn "tone_profile\|emotional_cues\|persona"` 只命中 AstrBot 自身的 persona 配置代码，**无一处引用 `persona/` 下的文件**。所以「把规则并入 `tone_profile.md` 的硬约束」是**零收益动作**——`tone_profile.md`／`emotional_cues.md` 是给人看的档案。任何"改完就该生效"的评审，先问一句「这条改在哪个文件、那个文件谁读」。
- **验收判据必须继承规则自带的豁免，否则判据比规则严，会把合规行为判成失败。** 实测：`system.txt` L5 的长度规则自己写着三个例外（问知识／要你展开／情绪与危机），而 CX-01 的验收判据只留了「每轮长度比 ≤2」；于是同一条回复可以「按 L19 不达标、按比值不达标、人工判通过」——**三套标准并存等于没有标准**。配套：① 逐轮比值在短输入上分母失真（2 字→上限 4 字），在长输入上过宽（30 字→60 字），两个方向反着错，**不能用统计量当逐条判据**；② 接住类场景需要**下限**，比值只给上限；③ 改判据通常**不用动定稿文件**，先别急着改提示词。
- **`……` 不是风格元素，是 C-02 的技术依赖。** `…` 不在 `Delete_Punctuation` 删除列表，而删标点钩子发生在分段之前，所以「故事断点固定用 `……`」是「用句号断点会静默切不开」这个 P0 的唯一规避手段。任何"她不用 `……`，删掉"的风格建议，先查 `docs/defect-register.md` §C-02——删它＝重开 P0。
- **断言"现状是什么"必须指名文件，因为同一项目里同名规则可能有三种口径。** 实测：`~`/`……`/`啧` 在 `prompts/system.txt` L5 是「很少用／只在互相开玩笑时偶尔用」，在 `persona/tone_profile.md` L11–L12 是「可以使用／偶尔使用」，而风格稿把两者混成一句「可以使用，不高频」并挂到 `system.txt` 名下 —— 引用一错，后面整段推理（"模型会照用"）的前提就没了。**引"现状"要带 `文件:行号`，且回读原文。**
