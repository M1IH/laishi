# WB-10 v2 复核（Codex，2026-10-23）

结论：**No-Go 判断成立；决策单需补件，暂不通过终验。** 以下问题会让未来的“24 小时已达成”或“工程门槛已勾完”出现假阳性。只修文档和只读探针，不动运行实例。

## 阻断项

1. **24 小时探针不能证明连续运行。** `data/probe_uptime.py:scan()` 在每个 `astrbot-YYYYMMDD.log` 开头重置 `cur`，跨午夜的同一进程被切成两段；只要某段有一次 `适配器已连接`，即使随后 QQ 掉线或进程停止而日志无新行，`main()` 仍可能给出“已达成”。`docs/pilot-go-no-go.md` §A-2、§六把这当充分放行判据，过强。补件：跨日按时间合并同一启动段，并把“日志可证明的启动/连接事实”与“持续在线尚未证明”分开；没有心跳或断连事件覆盖时，探针不得单独输出可放行的“已达成”。
2. **G1 的测试号验收步骤不可执行。** §一 G1 与 §六要求“测试号发一句 → 观察库新增 1 行”，但同文 G9 和 §A-4 已正确写明 `observer.target_qq` 当前指向来世，测试号消息不会入库。补件：在现配置下以测试号气泡和平台收发记录验收；如要观察库新增，先明确临时改为测试号并留痕回滚。这两种证据不得混写为同一必达条件。
3. **放行清单漏掉 G2。** §一将 C-09 分段送达列为 G2 未实现，但 §六勾选清单没有 G2，且“没勾的项写接受代价”允许把会影响历史与七日窗口的错误轻描淡写地跳过。补件：给 G2 明确的放行条件或明确的残余风险决定；不能只靠数气泡替代状态与历史一致性。

## 非阻断校准

- §A-5 的“今日启动次数要一直是 1”不适用于跨午夜继续运行：次日可为 0 且仍连续。应看当前启动段的起点与连续心跳。
- §二 D1 是 OTTO 已拍板的身份边界，改为“已定前提/代价提示”，不要重新列为待拍事项。
- §一 G5 的括号把 C-13 追问列在出站闸门覆盖范围，§六又正确写明 C-13 不归闸门；统一后者。

其余已核对：10 项矩阵覆盖了派单要求；G4/G5/G6/G7 与“规范通过不等于运行可用”的分层正确；24 小时总前置已如实记录为 OTTO 决定；陪伴效果候选指标没有被当作放行分数；文档没有私聊正文或账号。`data/probe_uptime.py` 用 Launcher 实例 Python 复跑，当前输出为 11 个启动标记、9 段未见连接、最长日志跨度 6h10m，**这些是日志观察值，不是已经验证过的历史最长真实在线时长**。

原三项阻断及三项校准均已落实；`data/probe_uptime_selftest.py` 用 Launcher 实例 Python 复跑 **19/19**，当前日志探针给 `NOT_REACHED`。**仍需两处最小补件，暂不关闭 WB-10：**
