## §1 出事了先做这三件事

```bash
cd "C:/Users/OTTO/Desktop/来世"
git status                 # 看谁被改了（M=改过，??=新文件）
git diff                   # 看具体改了哪几行
```

然后按情况选一条：

| 情况 | 命令 | 效果 |
|---|---|---|
| 某个文件被改坏，要还原 | `git restore 文件名` | 回到上次提交的样子（**新文件不受影响**） |
| 全部已跟踪文件改坏，全还原 | `git restore .` | 回到上次提交（**不删新文件**） |
| 多出一堆来历不明的临时文件 | `git clean -nd` 先看清单 → 确认后 `git clean -fd` | 删掉未跟踪文件（**不可恢复，先看清单**） |
| 想看看上次提交是什么样 | `git log --oneline -5` | 列存档点 |

**已实测**：`git restore README.md` 能还原被追加内容的文件；`git clean -fd` 能清掉新建文件；两次测试后 `git status` 均为空。

## §2 想留一个存档点（改代码前必做）

```bash
git add -A                              # 把当前状态放进待提交区
git commit -m "改了什么、为什么"          # 存档
```

规矩三条：
1. **一次改动一个提交**，别把几件不相干的事塞进一条。出问题时才能只退一半。
2. **提交说明写"为什么"**，不写"更新文件"。半年后你只看得懂原因。
3. **改坏了不要急着 commit**。先 `git status` / `git diff` 看清楚，觉得救不回来就 `git restore`。

## §4 四条铁律

1. **现在不推远端；将来要推，必须先过 §5 的清号闸。** 本仓库含三个真实 QQ 号（22 个文件）。**唯一不可逆的动作是 `push`**，本地怎么改都能重来。做 `git remote add` 就等于宣布"清号现在开始"——把这条当成信号，不要靠记性。
2. **不用 `git reset --hard`**，除非你已经 `git status` + `git diff` 看清楚了。它会把未提交的改动直接抹掉，git 不管。
3. **不改写历史**（`rebase -i`、`commit --amend` 堆在已提交的东西上、`filter-repo`）。本项目没有多人分支，改写历史只会让你自己看不懂。
4. **`.gitignore` 不要为了"想提交某个文件"去删规则。** 要放行单个文件，加一行 `!路径`，并在注释里写明为什么。

## §5 已知未清：三个 QQ 号在 22 个文件里

| 号码 | 指谁 | 涉及文件数 | 出现处数 |
|---|---|---|---|
| 来世本人 | 服务对象 | **18** | **37** |
| OTTO 本人 | 维护者 | **8** | **20** |
| Miruku 小号 | 机器人 | **8** | **10** |

三个号**并集 22 个文件**。分布最密的三处：`docs/chat-db.md`（来世号 7 次）、`docs/crisis-alert.md`（OTTO 号 7 次）、`knowledge/src/memes.json`（来世号 7 次）。其余散在 `docs/`、`persona/`、`WORK_LOG.md`、`.workbuddy/memory/`、`build_chat_db.py`、`data/probe_*.py`。

> **口径必须写清，否则每次都数不一样**（2026-10-24 15:5x 实测）：
> - 「出现处数」= `git grep -o <号> -- . | wc -l`，即**匹配片段数**（一行两个号算 2）。
> - `git grep -c` 给的是**行数**（一行两个号算 1），比上面小。
> - **别在数字外面套 `\b`**：中文正文里 `\b` 会漏匹配，实测同一个号从 **37 次掉到 18 次**，看数字像是"已经清掉一半"，其实一个都没少。
>
> 所以：**改完要按同一口径重数，别拿两种口径的数字互相比。**

### 5.1 挂起规则（OTTO 2026-10-24 决定：等项目完成后清）

**这不是"待定"，是"有时钟的挂起"。** 解冻条件只有一条：

> **第一次 `git push` 之前。** 不是"项目完成"，不是"想推的时候顺手"。

两者不等价，有四条现实路径会让 push 远早于"项目完成"：

| 会提前 push 的情形 | 为什么 |
|---|---|
| **上云部署用 `git clone` 拉代码** | 要 clone 就先得有远端 → 部署当天就是 push 当天。而部署远早于项目完成 |
| 想把进度当备份放上去 | 备份是个连续动作，不是终点动作 |
| 想让别人（或别的 AI）看 | 只有"本机读文件"不需要推；一旦要给链接，就已经推出去了 |
| 想加 CI / Actions | 同上 |

**判断口诀**：不是"项目完成了吗"，而是**"这条命令会不会让代码离开这台电脑"**。

> **私有仓库也不能免清。** 三个理由：① 私有库对协作者、组织成员，以及 GitHub 自己的运维面都是可见的；② 一次误点"转公开"或账号被盗就变成永久公开，**这个失误不可撤销**；③ 来世的号是**第三方的隐私**——不是你自己同意就能处置的东西。所以闸门设在 `push` 之前，不设在"公开"之前。

### 5.2 这个决定有一个确定的代价（不是风险，是必然发生）

「等项目完成再清」会让清理方式从 A 升级到 B：

| | 什么时候做 | 怎么做 | 代价 |
|---|---|---|---|
| **路 A** | 提交数还少时（现在是 **2 个**） | `rm -rf .git` → 重建基线 | **只丢提交历史**，而历史本来就只有两次快照，等于零成本 |
| **路 B** | 几十上百个提交之后 | `git filter-repo --replace-text` 逐号替换 | 要装工具、**所有 commit hash 全变**、操作复杂、出错面大 |

所以：**"完成后再清"＝默认选了 B**。如果只是懒得多做一步，A 现在就可以做；如果是因为**现在清会动到 `data/probe_*.py` 里那两处断言、可能打坏 Codex 正在跑的探针**，那这个理由是成立的，按挂起走，但要在推之前留出时间做 B。

**路 B 的骨架**（到时候命令别再查一遍，容易抄错）。**注意本文档零账号**：号码不抄在这里，下面用 `$Q1/$Q2/$Q3` 占位，取值见 §5.5 第一条命令：

```bash
pip install git-filter-repo        # 装到 venv，或加 --user
printf "$Q1==><TARGET_QQ>\n$Q2==><OWNER_QQ>\n$Q3==><BOT_QQ>\n" > replace.txt
git filter-repo --replace-text replace.txt --force
```

两个必须知道的行为：① **所有 commit hash 会全变**（历史结构保留，指纹全变）；② **它会自动删掉 remote 和 reflog**，这是它故意的安全设计。所以**不要在已经 push 过的仓库上做**——那时已经太晚，B 只能清本地，清不掉远端。

### 5.3 为什么当初没在首次提交前清

这批号码里有一部分**不是注释，是运行资产与验收断言**：

- `data/probe_inject_hook.py`、`data/probe_knowledge_adversarial.py` 里的 `assert TARGET != <号码>` —— 替换成占位符会变成**恒真**，探针当场作废，而且之后"全部通过"看起来更正常。
- `knowledge/src/memes.json`、`persona/` 里的出现位置需要逐个判断是数据还是说明。

**批量 sed 会同时打坏基线和 Codex 正在跑的探针**，所以没有擅自做。

### 5.4 清的时候怎么判断（三类，不要按文件逐个瞎猜）

| 类型 | 特征 | 改法 |
|---|---|---|
| **断言值** | 出现在 `assert` / `if ... ==` / 白名单数组里 | **不能换成占位符**，改成从配置读（`data/cmd_config.json` 或运行配置），保留"读不到就失败"的语义 |
| **运行数据** | `knowledge/src/*.json`、`persona/*.md` 里的具体号 | 换成占位符（如 `<TARGET_QQ>`），并确认注入逻辑不依赖字面量 |
| **散文/注释** | 文档正文里写"来世的号是 xxx" | 直接换成角色名（"来世本人"/"OTTO 本人"/"机器人小号"），不损失可读性 |

### 5.5 清完必须验（缺一条都不算清干净）

```bash
# 0. 三个号现取（本文档不存号码）。看前三名，人工确认就是 §5 表里那三个
#    注意：不要给数字套 \b，中文正文下会漏匹配（见 §5 口径注）
git grep -ohE '[1-9][0-9]{8,10}' -- . | sort | uniq -c | sort -rn | head -5
Q1=<来世号>; Q2=<OTTO号>; Q3=<机器人号>   # 把上面看到的填进来

# 1. 工作区 + 提交历史 里都必须为 0
git grep -l -E "$Q1|$Q2|$Q3" -- . ; echo "(工作区：应无输出)"
git log -p | grep -cE "$Q1|$Q2|$Q3" ; echo "(历史：应为 0)"

# 2. 探针必须逐个重跑（尤其两个带 assert 的），断言不许变弱
PY="C:/Users/OTTO/.astrbot_launcher/instances/298681be-6ba8-4137-818c-28ed67ec9176/venv/Scripts/python.exe"
$PY data/probe_inject_hook.py
$PY data/probe_knowledge_adversarial.py

# 3. 重建仓库后确认只有预期的提交数
git rev-list --count HEAD
```

**第 1 步的历史检查是关键**：只改文件不重建仓库，等于没清——`git log -p` 里原始号码还在，`push` 会连带历史一起推上去。

## §6 给外部 AI 的约束

`docs/prompt-for-claude.md` 已规定它只能只读审计。补一条 git 相关：

- **允许**：`git status`、`git diff`、`git log`（只读，用来证明它改了什么）。
- **禁止**：`git commit`、`git restore`、`git clean`、`git reset`、`git checkout <分支>`、`git stash`——这些会改动你的工作区，属于写操作。
- 它报"我改了什么"时，**必须贴 `git diff` 原文**，不许只说"已优化"。

## §7 一句话备忘

> **改之前想清楚要改哪几个文件；改完先 `git diff` 看一眼；确认好了再 `git commit`。**
> git 只保护它看管的东西——配置、日志、聊天记录都不在里面。

> **推之前先过 §5 清号闸。** 判断不是"项目完成了吗"，而是"这条命令会不会让代码离开这台电脑"——`git remote add` 那一刻，就当作清号开始。
