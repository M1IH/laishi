## 一、结论先说

Codex 的 5 条**全部成立**，而且每一条都能复现。其中第 1、3、5 条是**结构性错误，不是措辞问题**：

| # | Codex 的判断 | 我的定性 |
|---|---|---|
| 1 | `event_id` 同时当"内容指纹"和"发生唯一 ID"，同名文件覆盖 | **真错误**。我把两个生命周期完全不同的身份合并了 |
| 2 | 8 位哈希"必然不同"是绝对断言，不成立 | **真错误**。32 位熵在几千事件量级就会碰 |
| 3 | "只有 acked 才停补发" 与 "45 分钟后停止" 直接矛盾 | **真错误**。我把两个正交状态写成了一个 |
| 4 | "不重发不追问" 与 "补问一次" 两条规则并存 | 成立（真实歧义）。是同一件事的两面，但没写清次数归属 |
| 5 | B 档次日汇总属于 OTTO 未授权的额外推送 | **成立，且是我越权**。授权边界是"发一次"，我不能自行加一条 |

第 5 条我想多说一句：这不是技术错误，是**规范自行提高了打扰预算**。它听起来更"负责"，
但"更负责"不等于"可以替 OTTO 决定多打扰他一次"。这类改动只能由 OTTO 拍板。

## 二、五项修订的前后差异

### 第 1 项：`fingerprint` 与 `occurrence_id` 分离

| | v2（错误） | v3 |
|---|---|---|
| 身份数量 | 一个 `event_id` | **两个**：`fingerprint`（内容）+ `occurrence_id`（发生） |
| `fingerprint` | `sha1(...)[:8]` | `sha256(...)` **64 位全量，不截断** |
| `occurrence_id` | 不存在 | `f"{fingerprint}__{occurred_at:%Y%m%dT%H%M%S}{rand4}"` |
| 文件名 | `events/<event_id>.json` → **同名必覆盖** | `events/<occurrence_id>.json` → **每次发生一个新文件** |
| ack 粒度 | 内容 | **这一次发生** |
| 窗口判断用谁 | `event_id` | `fingerprint`（glob `events/<fp>__*.json` 取 `occurred_at` 最大者） |
| 序号方案 | `occurrence += 1`（要扫描后 +1） | **不用序号**：序号在"文件被手工删/锁失效"时会撞，撞了就是覆盖；改用时间戳 + 4 位随机 |

**关键区别一句话**：`fingerprint` 回答"是不是同一句话"，`occurrence_id` 回答"这是哪一次"。
前者一个内容一个，后者一次发生一个。混用就必然出现"6 小时后的同一句话覆盖 6 小时前那条"。

**文件名长度**：64 hex + `__` + `20261021T231405` + 4 = 约 85 字符，路径总长在 Windows 上限内。
落盘前**必须再查一次同名文件是否存在**，存在就重新生成 `rand4`——这是"永不覆盖"的最后一道保证。

### 第 2 项：不截断 + 删掉"必然不同"

| | v2（错误） | v3 |
|---|---|---|
| 断言 | "不同 `excerpt` **必然**不同 `event_id`" | **删除**。改为可执行判据，不再做概率承诺 |
| 截断 | 8 位十六进制（32 bit） | **64 位全量**，不截断 |
| 碰撞判据 | 无 | 指纹相同 **且** `text_len` 相同 → 同一句话；指纹相同但 `text_len` 不同 → **拒绝合并** |
| 碰撞处置 | 无（静默合并） | 新建 occurrence + `alerts.jsonl` 记 `fingerprint_conflict` + `PENDING.md` 人工核查 |
| 存什么 | 只存 ≤30 字 `excerpt` | 另存 `text_len`（**存长度不存全文**：够当判据，又不扩大隐私暴露面） |

**为什么这样改是对的**：Codex 说得对——"8 位哈希不撞"是概率问题，不是逻辑保证。
但只要指纹只承担"这是不是同一句话"，**唯一性由 `occurrence_id` 单独保证**，这个概率问题就不再有后果。
真正需要防的是"碰撞后静默合并"，所以加了 `text_len` 判据 + 冲突告警。

### 第 3 项：`ack_state` 与 `resend_state` 正交

这是 v2 **最严重**的一处，因为它是两句互相抵消的话。

| | v2（自相矛盾） | v3 |
|---|---|---|
| 表述 | §3 写"**只有 `acked` 才能停止补发**"；§7 写"45 分钟后**停止补发**" | 拆成两个字段：`ack_state`（人的确认）/ `resend_state`（提醒计划生命周期） |
| 45 分钟后 | 语义不清：算"停了"还是"没确认"？ | `resend_state = exhausted`，**`ack_state` 仍是 `unacked`** |
| 重启 | 只说"未 ack 的补发" | 四种分支写死（见下） |
| 防偷记 | 无 | **字段层面不给写的机会**：`acked_at` 只能由 `alert_ack.py` 写；超时逻辑禁止触碰 |
| 措辞 | "已停止补发"（易读成已处理） | 统一写 **「已停止自动提醒（未确认）」** |

**重启的四种分支**（v2 完全没写，是 Codex 第 3 项的实质）：

| 重启时的状态 | 行为 |
|---|---|
| `active`，`now < next_resend_at` | 继续等，**不立即发** |
| `active`，`now ≥ next_resend_at`，`resend_count < 3` | 立刻补发一次（正文标"重启补发"），推进 slot |
| `active`，但已过**最后一个** slot | 转 `exhausted`，`resend_exhausted_at` 记**实际发现时间**，**不补 3 次、也不假装补过** |
| `exhausted` / `stopped_by_ack` | 保持，只出现在 `PENDING.md` |

第 3 行是重点：**电脑关了两天再开机，不能突然补发 3 条两前的告警。** 那不叫补发，叫骚扰。

### 第 4 项：把两条次数规则合成一个计数器

| | v2（歧义） | v3 |
|---|---|---|
| 记法 | `inline_asked` **布尔** + 三条文字规则 | `safety_ask_count` **整数，上限 2**，两个固定槽位 |
| "对方不回复不重发" | §3 第 3 步 | 保留，但明确它指的是 **#2 之后永无第三次** |
| "补问一次" | §3 互斥规则 | 就是那唯一的 **#2**，不是额外一次 |
| 槽位定义 | 无 | #1 = 即时层；#2 = 后续层，**仅当 #1 已用且未获回应**；若 #1 没用掉则 #2 顶替 |
| 授权性质 | 未说明 | **明确写出：这是 OTTO 2026-10-21 授权的"发一次"之内，不是授权扩张** |
| 危险回应 | 未处理，与"最多 2 次"冲突 | **开新 episode、计数器归零**，否则 L21 三步行动里的"再确认一次"永远发不出去 |
| 持久化 | `inline_asked` | `safety_ask_count`（布尔记不了"问了几次"，而次数才是唯一依据） |

**为什么必须用整数**：布尔只能回答"问过没有"，回答不了"还能不能问"。
v2 之所以读起来像两条打架的规则，根因就是**次数信息在布尔里丢失了**，只能靠文字描述补，一补就自相矛盾。

### 第 5 项：撤回 B 档次日汇总

| | v2（越权） | v3 |
|---|---|---|
| B 超限 | 第 5 条起改为**次日 12:00 一条汇总** | **不推送、不发汇总**，只写 `alerts.jsonl` + `suppressed_push_count` + PENDING 计数行 |
| 授权依据 | 无（我自己加的） | OTTO 边界：B 档「发一次、不补发、不确认」。**汇总是一条新推送，超边界** |
| 告知 OTTO 的方式 | 新推送 | **搭车**：附着在下一条本来就要发的消息尾部（不新增打扰次数） |
| 代价 | 未声明 | **明确写出代价**：若当天既无 A 也无未超限 B，OTTO 就不知道有 N 条被压掉 |
| 决策归属 | 被我写成"已定" | **列为待 OTTO 拍板**（§8.3），我只给建议 |

**搭车行为什么比汇总好**：汇总每天准时到、内容永远是"N 条 B"，它几乎注定变成被忽略的那一条；
而搭车行只出现在本来就重要的消息旁边，看到它的人正在认真看那条消息。

## 三、新增：状态转移表（正文在 `crisis-alert.md` §8之二）

表覆盖 Codex 点名的 7 类：同句 6h 内重复 / 6h 后重复 / ack 后重复 / 两个不同事件 /
45 分钟后仍未 ack / 重启（三种分支）/ B 超限。摘要：

| # | 情形 | 新建文件？ | 推送？ | 终态要点 |
|---|---|---|---|---|
| T1 | 同句 < 6h，未 ack | 否 | 否 | `seen_count += 1` |
| T2 | 同句 ≥ 6h，未 ack | **是** | 是 | **旧文件原样保留**，两条都可同时在 PENDING |
| T3 | 同句，已 ack | **是** | 是（< 30min 则延后） | 旧事件 `acked` 不受影响 |
| T4 | 两个不同内容 | 两个文件 | 两条都发 | 互不影响 |
| T5 | 45min 后仍未 ack | 否 | 停 | `exhausted` + `ack_state` 仍 `unacked` |
| T6a/b/c | 重启三分支 | 否 | 视分支 | **已过全部 slot 不补 3 次** |
| T7 | B 第 5 条 | 否 | **否，无汇总** | 计数 + 搭车行 |
| T12 | 同指纹不同 `text_len` | 是 | 是 | 记 `fingerprint_conflict` |

### 手工演算：Codex 举的那个反例（同一句话 6 小时后重现）


| **F16** | 休眠跨夜后开机 | 启动补扫生成"延迟告警"，首行标离线时长；与重启补发**不重复** | 重复告警 → 启动补扫未查 `fingerprint` |

- `alert_ack.py` 连跑两次 → 第二次无副作用。
- 两个 alerter 同时启动 → 第二个直接退出，只发一条。
- 把事件文件里 `ack_state` 改成 `"acked"` 但 `acked_at` 留 `null` → 启动必须判为**损坏并拒绝加载**，
  不允许"字段不一致时猜一个"。

## 六、仍需 OTTO 做价值取舍（单列，未代拍板）

1. **B 超限后要不要一条次日汇总？**（`crisis-alert.md` §8.3）
   - 现状默认 **不要**（零额外推送，靠搭车行）。代价：某些日子 OTTO 完全不知道有 N 条被压掉。
   - 选"要"的代价：多一次固定打扰，且这条汇总极易变成被忽略的那条。
   - **我的建议：不要**。但这是我第二次提到它，说明它确实是个有价值的取舍点——所以留给你。

2. **是否改用独立 QQ 号接收告警。**
   - 现状：OTTO 私聊既是测试会话又是告警箱，需额外做上下文隔离。
   - 用独立号：加一次好友 + 改一行常量，换取 §5.3 整节风险消失。
   - **我的建议：v1 先按现状隔离**，等告警真的开始用再决定。

除上述两点，`crisis-alert.md` 已无待决项；OTTO 已拍板的 A/B 告警范围、A 档措辞、L3 不启用**均未改动**。
