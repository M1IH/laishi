### A-2 「连续」怎么算（判据写死，改判据等于改结论）

> **v4 重写。** v3 的判据有一个方向性错误：把 `适配器已连接` 当成"此刻在线"的证据点，于是**重连越频繁，证据点越密，越容易判达成**。事实正好相反。

**先分两类证据，不许混：**

| 类型 | 长什么样 | 能证明什么 | 能不能当心跳 |
|---|---|---|---|
| **链路事件（LINK）** | `aiocqhttp_platform_adapter:107`（`适配器已连接`） | **某一刻连上过** | **不能**。重复出现＝重连＝中间断过 |
| **持续在线心跳（BEAT）** | 周期性出现的"活着＋适配器在线"行 | **此刻仍在线** | **能**。当前 `HEARTBEAT_MARKS = ()`，**一条都没有** |
| **旁证（不参与判定）** | NapCat `二维码已被扫描`／`登录成功`／`账号状态变更为在线` | 扫码 ≠ 登录成功 ≠ 适配器可用 | 不能。只打印，不进判定 |

**判据（顺序即优先级）：**

1. **一次启动** = 日志出现 `core.main:144`（进程每次启动都打印 ASCII banner）。
2. **跨午夜按时间合并**：日志按日切文件，**进程不按日重启**。所有日志先合成一条时间轴流再切段——没有新 banner 就是同一段，跨几个文件都算一段。（旧版按文件重置，会把一个跨夜进程错切成两段，已修，见 `probe_uptime_selftest.py` 样例 1／8。）
3. **一次重启** = 计时**归零**，前后两段不相接。
4. **段长 < 24h** → `NOT_REACHED`。
5. **段内一次 LINK 都没有** → `NOT_REACHED`（进程在跑，什么都没接到）。
6. **段内 LINK ≥ 2 次** → **`BROKEN`**。第二次"已连接"在语义上就是"此前已经断开过"，**不需要等到看见断连日志**。重连即中断，24h 归零。
7. **段内有掉线事件**（NapCat `账号状态变更为离线`／`KickedOffLine`／`登录已失效`）→ `BROKEN`。
8. **没有心跳**（`HEARTBEAT_MARKS` 为空，或段内 0 拍）→ **`UNPROVEN`**。**这条与日志内容无关**：哪怕某段跑了 30 天、只连过一次、一次没掉线，也只能是 `UNPROVEN`。
9. **心跳最长空档 > 10 分钟** → `UNPROVEN`。
10. 以上全过 → `PROVEN`（段长 ≥24h ＋ 只连一次 ＋ 无掉线 ＋ 心跳空档 ≤10min）。

**输出四档，别混**：`NOT_REACHED`（时长不够／从未连上）／`BROKEN`（段内断过，必须归零）／`UNPROVEN`（时长够、连上过，但持续在线未证明）／`PROVEN`（需先有心跳；**当前结构上不可达**）。

**在第 8 条成立之前，`PROVEN` 不是"努力方向"，是"不可达状态"。** 要让这句话可推翻，唯一办法是让心跳真落地，不是改判据、不是换证据、不是把别的日志行当心跳。

### A-3 中断的定义与归零

**算中断**（任一发生即归零）：
- 新的 `core.main:144`（进程重启）；
- **段内第二次出现 `适配器已连接`**（v4 明确：**重连本身就是中断证据，不需要再看到断连日志**）；
- NapCat 出现 `账号状态变更为离线` / `KickedOffLine` / `登录已失效`（掉线或被踢）。

**归零规则**：从 0 重算，**不许累计**。累计 24 小时毫无意义——要验的是"能不能连续跑"，不是"总共跑过多久"。
**没有例外**：因维护必须重启 → 那次 24h 作废，从头开始。这条写死，是因为"这次不算"是所有计时失效的起点。

> **v4 加这一条的理由**：旧判据里"重连"只是"多一个证据点"，等于**断得越多，看起来越健康**。这是把反向信号当正向信号用。现在的处理是：**重连一次就作废这段**，让"断"这个事实不可能被误读成"在线"。
