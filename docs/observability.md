# Miruku 最小原始事件记录

更新时间：2026-10-20

## 已落地

`plugins/astrbot_plugin_miruku_observer/` 是 AstrBot 观察插件，不修改消息、不调用模型、不触发发送。它只对配置的 `platform_id` 与 `target_qq` 的私聊工作。2026-10-20 已安装到当前 Launcher 实例，插件处于启用状态，目标配置已写入实例本地配置；原始代码保留在项目目录。

SQLite 位置：AstrBot 实例的 `data/plugin_data/astrbot_plugin_miruku_observer/events.sqlite3`。每个观察事件只保存方向（peer/bot）、UTC 观察时间、目标与入站消息 ID 的 SHA-256 摘要，以及对方在 Bot 发言后的**首次**回复间隔。不会保存正文、昵称或原始 QQ 号。相同入站消息 ID 会去重。所有写入失败只记异常类型，避免把内容写进日志。

事件表预留 `low_mode_triggered`、`crisis_mode_triggered` 两列，目前均为 `NULL`，表示**未知**。AstrBot 当前的人格模式切换发生在提示词与模型内部，没有结构化“模式已触发”事件；不能用关键词猜测填入真/假。用户尚未确定“陪伴效果好”的评价标准，因此这些原始事件也不自动计算效果分数。

## 验证与边界

- 已在 Launcher 实例 Python 环境验证：事件去重、首次回复间隔、模式未知值、数据库不含原始 QQ；插件模块可导入
- 已通过 AstrBot API 确认插件重启后启用、目标配置存在，SQLite 已创建
- 2026-10-20 运行库已有目标 QQ 的 4 条入站、3 条普通回复出站事件，以及 2 条首次回复间隔；仅核对元数据，未读取正文。普通私聊链路已获得真实事件证据
- AstrBot 的 `platform_message_history` 在检查时仅有 1 条 QQ 平台记录，不能把它当作完整历史消息源
- WorkBuddy 审计确认主动消息直发绕过 `after_message_sent`。观察插件现增加只读轮询 `platform_message_history` 的目标 bot 行，按历史流水 ID 去重并用流水时间补记 bot 事件；收到 peer 消息前先同步，以降低短间隔回复漏记。已在 Launcher 实例 Python 中用合成流水验证 42 秒回复间隔、重复轮询不重复写入，并在运行实例重载插件。**目标 QQ 的主动消息尚未实际发送，因此这条桥接链路仍待真实主动消息验收**。此实现依赖当前 AstrBot 的 `platform_message_history` schema；升级后需复核
- 2026-10-20 12:17–12:24（CST）复核：目标 QQ 的真实私聊事件已入库，共 7 条原始事件（4 条入站、3 条出站），含 2 条首次回复间隔（14.93s、131.49s）。来世本人受 OTTO 邀请发送了三条测试消息（“1”“你喝牛奶吗”“你会不会舞萌dx”）并收到回复，入站/出站链路已用真实私聊验收；此前“事件库按 `message_events` 表统计仍为 0 条”的结论已过时
- “每次会话消息条数”将由原始时间与方向事件按后续约定的会话边界计算；目前没有擅自规定沉默多久算新会话

实例配置与事件数据库属于本地运行数据，不纳入代码仓库。部署到其他实例时先复制插件，再通过 AstrBot WebUI 设置平台 ID 和目标 QQ；`target_qq` 为空时插件不记录任何事件。
