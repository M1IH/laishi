## 零、先给结论

**有用，但只在一个很窄的条件下有用：同一批数据、同一口径、样本量 ≥ 数百条，比的是分布而不是分数。**

1. **它已经证明了自己三次**：①推翻了「v2 有明显改善」的直觉（真实提升只有 D1 那一项）；②逼出了 `conversations.content` 的 repr 污染（212 回合正文是原始 Python 字面量）；③逼出了「回合 vs 条」的口径错误（发送层会把一条回复拆成多条 QQ 消息）。这三个发现都不是靠肉眼能看出来的。
2. **但它的绝对分数不能跨批次比**：同一批数据随机切成两半，两半分差**中位 10 分**、p90 17 分、最大 27 分。所以「这次 86、上次 83」这种 3 分之差**在噪声里，没有意义**。
3. **它现在完全靠人记得才跑**：仓库里没有任何插件、脚本或定时任务调用它，`data/tone_golden.json`（规范 §9 要求的黄金用例）**至今不存在**。
4. **批次模式从不检查红线**：`redlines()` 只被 `score_single()`（`data/tone_score.py:275`）调用，`score_batch()`（`:360`）完全没调。也就是说 R1–R5 五条红线在批量评分里是**死代码**。
5. **D3 在小样本下极不稳定**：扣分按「每 100 回合」折算（`d3_scale = 100.0/n`），1 次命中在 87 条样本里扣 8.0 分，在 552 条里只扣 1.3 分。

## 二、它的分数稳不稳（信度检验）

### 2.1 随机切半

把 OLD 普通 427 条随机分成两半，各算一次分，重复 200 次：

| 指标 | 值 |
|---|---|
| 两半分差 \|A−B\| 中位 | **10 分** |
| p75 | 14 分 |
| p90 | 17 分 |
| 最大 | 27 分 |
| 半样本分数范围 | **52 ~ 80**（中位 58） |

**同一批数据、同一时期、只是随机分成两半，就能差出 10 分。** 结论：单次跑出的绝对分数，置信区间大约是 **±10 分**。

### 2.2 抽样分布（同尺寸对比）

各抽 50 / 60 条，重复 300 次：

| 样本 | 抽 50 条 | 抽 60 条 |
|---|---|---|
| OLD 普通（427 条池） | 中位 **61**，p10 52，p90 85，范围 47~94 | 中位 **61**，范围 48~93 |
| NEW 普通（87 条池） | 中位 **81**，p10 79，p90 94，范围 78~95 | 中位 **82**，范围 81~95 |

**这个对比是可信的**：OLD 中位 61、NEW 中位 81，差 20 分，远超 ±10 的噪声。所以「新版确实比旧版好」这个方向性结论成立。

> 注意 NEW 的范围窄（78~95）是因为池子只有 87 条，抽样接近全取，方差天然小。不能拿「NEW 方差小」当稳定性证据。

### 2.3 「取最近 N 条」是有偏的

| 取法 | 分数 |
|---|---|
| OLD 普通**全部** 427 条 | 58 D |
| OLD 普通**最后** 87 条 | **83 B** |
| OLD 普通**随机** 87 条 | 约 **63** |

同样是 87 条，取末尾比随机取高 **20 分**。原因是旧段里 10-20 那批「描述表情包」的垃圾回复集中在最前面。

**教训：以后所有新旧对比都必须用「随机抽样 + 重复多次」，不能用「最近 N 条」。** 2026-11-10 那份报告里的「同尺寸 86 vs 83」正是踩了这个坑——87 比 83 那 3 分是取法造成的，不是真实差距。

**真实故事不是「一路变好」**：

## 四、它的结构性缺陷（按严重程度）

### 4.1 批次模式不检查红线（P0）

> **已修（v1.2）**：`score_batch()` 现在在 `score_batch_raw()` 开头逐条原文跑 `redlines()`，用**未清洗**的原文（`clean()` 会剥掉 `<system_reminder>`，而 R1 要抓的正是它）。红线只统计频次、不折算成分数，与第 0 层「整条作废」语义一致。427 条旧语料抓到 R1/R2/R4 各 1 次，此前恒为 0。

`redlines()` 只在单条模式调用。批量评分里：

```python
# data/tone_score.py:360  score_batch() 全文没有 redlines 调用
```

后果：R5「思考泄漏」（`<thought>`、`思考：`、`（内心`）在批量数据里**永远不会被统计到**。R1–R4 同理。也就是说「五条红线一票否决」这个设计，在唯一被实际使用的批量模式里是**不生效的**。

### 4.2 D3 的每百回合折算让它对样本量过敏（P0）

> **已修（v1.2）**：改成饱和曲线：`D3 = 35 × (1 − min(1, 每百条扣分 / 100))`。同命中率下 100 / 200 / 500 条得分完全一致（`probe_invariant.py` 验证 12 组全等）。饱和点 100 分的含义是「每百条约 14 次 C3 就彻底失控」，真实语料最坏的一天（2026-10-20，118.4 分/百条）正好封顶。D4 同构。

```python
d3_scale = 100.0 / n          # :410
d3_raw = W["D3"] + sum(d["delta"] for d in d3_hits) * d3_scale
```

| 样本量 | 1 次 C2 命中（-7）实际扣分 |
|---|---|
| 87 条 | 8.0 分 |
| 135 条 | 5.2 分 |
| 552 条 | 1.3 分 |

这导致两个后果：①小样本批次分数天然更低；②**一次误报就能把一个 87 条的批次从 A 打到 B**。实测 NEW 普通 87 条里唯一一次 C2 命中是 `你这是在教我念咒语吗`（用户上句「比比拉布」），**接得很自然，属于误报**。

### 4.3 C2 正则会误伤正常接话（P1）

> **已修（v1.2）**：`C2_PAT` 已排除 `是在` 后接动作动词（教/做/干/玩/唱/念/写/画/比划/说/发/整）的情形，并补 `么` 收尾。687 条语料：旧正则 6 次命中含 2 个误报，新正则 4 次全为真阳性。`SELFTEST` 里那条把误报当正确答案的用例改成负向用例，并加了「反向断言」——`want_codes` 没列出的 C1~C3 不得命中。

```python
C2_PAT = re.compile(r"(是想|是要|是在|大概想|是不是想).{0,16}(吗|吧|？)")   # :69
```

实测误报：`你这是在教我念咒语吗`。规则本意是抓「你是在说 X 吧」这种替对方下结论，但「这是在…吗」是正常疑问。

**更严重的是，自检用例把这个误报固化成了「正确答案」**（`data/tone_score.py:475`）：

```python
("在呢，来世是在试 Miruku 有没有反应吗", "daily", "B", ["C2"]),
```

这句接得很自然，本身不该扣分，但它被写进 `SELFTEST` 并且要求必须命中 `C2`。也就是说：**`--selftest` 7/7 全绿这件事，有 1/7 是在验证一个错误行为**。改 C2 正则之前得先把这条用例改掉，否则一改就「自检失败」。

### 4.4 没有黄金用例（P1）

> **已修（v1.2）**：已建 `data/tone_golden.json`（32 条，覆盖 §8 的 daily≥5 / emotion≥3 / crisis≥2 / 各扣分项典型≥10），配套 `--golden` 运行器，`must_hit` / `must_not_hit` / `expected_grade ±1 级` 三种断言，门槛 95%。当前 32/32 通过。

`docs/tone-rubric-spec.md:291` 写明「改评分逻辑后必须跑 `data/tone_golden.json` 对照」，但该文件**从未创建**。所以 §9 的变更保护是空条款。目前唯一的回归保护是 `--selftest` 的 7 条内置断言（只覆盖单条模式）。

### 4.5 口径依赖外部约定，容易被误用（P2）

`--turns` 吃的是回合级 JSON，必须先跑 `.tmp-tone/expand_msgs.py` 展开成「条」才是正确口径。而 `--recent` / `--limit` 是**回合级**截断，不是条级。这两个陷阱在 2026-11-07 和 2026-11-10 各踩了一次，两次都得出过错误结论。

**两处与 v1.1 相反的结论，说明 v1.1 的分数不能直接比**：

1. **OLD 普通 427 条：58 D → 78 B**。原因不是语料变了，是口径变了 —— v1.1 把红线命中（R1/R2/R4 各 1 次）当普通扣分混进 D3，v1.2 把它们分离出来只记频次；同时 D3 从线性折算改饱和曲线。
2. **OLD 普通前 87 条：83 B → 53 D**。这批 10-20 的语料 D3 命中率 118.4 分/百条，v1.1 的 `× 100/n` 让它在 87 条上只扣约一半、拿到 26/35，v1.2 的饱和曲线如实判为 0 —— 这才是「那两天确实很糟」的正确读数。

**因此**：跨版本比分数没有意义，比同一版本内的相对关系才有意义。v1.2 下 **NEW 普通 94 vs OLD 普通前 87 条 53**（同为 87 条）差 41 分，方向性结论比 v1.1 的 3 分差距得多 —— 因为 v1.1 的两边都被同一个折算口径污染了。

**已知仍存在的局限**（v1.2 未解决）：`NEW 主动` 只有 48 条，够不到 `MIN_SAMPLE = 50`，主动消息这条线仍然出不了分；`pain` 场景在 v2 之后依然 0 条，所以「是否为求短而漏接情绪」仍然无法验证。
