## 待工程侧处理（Codex）

1. **工具调用标记泄漏成正文**（严重）。`logs/astrbot-20261020.log:335-339`，2026-10-20 12:38:21，respond stage 把 `<system_reminder>…</｜｜DSML｜｜ parameter>` 这类 DSML 语法当成回复发出。模型侧已加「不输出工具标记」的约束，但根因在工具调用解析/降级路径：解析失败时应丢弃而不是按纯文本发送。
2. **`astrbot_execute_python` 被权限拒绝**。12:37:08 模型试图用 `time.sleep(2.5)` 制造分段停顿，报 `Permission denied. Python execution is disabled by the Local permission policy for this user role (member)`。提示词已改为「不要用 sleep/代码制造停顿」；若确实需要「两条消息之间停一下」，应由发送层（插件/工具）提供，而不是让模型 sleep。
3. **`astrbot_humanlike` 的两个配置需要产品决策**：
   - `Ignore_Randomly` 当前开启，概率 10%。这意味着约十分之一的私聊会被**完全静默忽略**；对陪伴型机器人偏危险，尤其对方发来低落/危机消息时。建议关闭，或至少对目标会话与低落/危机关键词豁免。
   - `Late_Interventions`（发言延迟 1–10 秒）当前关闭。若想要「先停顿再回应」的自然感，这是现成的开关；但它延迟的是整条回复，不是两条消息之间。
   - `Punctuation.Delete_Punctuation` 实际不生效：该 handler 的结果会在此后被 `event.clear_result()` 清掉（AstrBot `pipeline/process_stage/method/star_request.py`），所以它既不会删回复里的标点，也不会删危机句的「？」。不要把它当作标点策略依赖。
4. **流式输出与预发送钩子**。`result_decorate.stage:169` 警告：启用 streaming 时依赖 pre-send 钩子的插件可能失效。webchat 探针即因此把 `<thought>` 和 `[Profile: …]` 原样显示出来；QQ（aiocqhttp）非流式，实测 12:21 回复干净。建议只把 webchat 当调试窗口，验收仍以 QQ 为准。
