# Miruku 语言评分细则（设计说明 v1.0）

> 建立：2026-11-06　定稿：2026-11-07（OTTO 已拍板四项参数）
> 目的：把「像不像人」从感觉变成可复现的分数，用来（a）判单条回复该不该发，（b）追踪趋势是否在变好。
> **规范正文见 [`docs/tone-rubric-spec.md`](tone-rubric-spec.md)**——本文只讲为什么这么设计，冲突时以规范正文为准。

---

## 一、为什么现有脚本不够

现有三份东西各管一段，但都没有「判分」：

| 已有 | 管什么 | 缺什么 |
|---|---|---|
| `data/tone_stats.py` | 算真实语料与机器人的长度/人称/标点**分布** | 只有分布，没有阈值、没有分数、没有「哪条该扣分」 |
| `data/probe_reply_metrics.py` | 5 条硬判据（中位 ≤15、P90 ≤30、长度比 ≤2、问句收尾 ≤15%） | 判据太松（中位 15 字是真人 4 字的 3.75 倍），且不管词汇层 |
| `astrbot_plugin_miruku_metrics` | 回合级行为（轮数、冷场、主动消息回复率、话轮比） | 完全不管文本长什么样 |

**根本缺口**：没有一个东西能回答「她这句话，AI 味有多重，重在哪一项」。

## 二、先厘清一件事：AI 味到底是什么

用本项目自己测出来的数据看（`persona/tone_profile.md`，9,380 条真实语料 vs 93 条测试期机器人）：

| 指标 | 来世（真人） | 测试期机器人 | 差异 |
|---|---|---|---|
| 中位长度 | **4 字** | 14 字 | 3.5× |
| 均值 | 5.3 字 | 21.4 字 | 4× |
| ≤10 字占比 | **94%** | 33% | — |
| p90 | **9 字** | 31 字 | 3.4× |
| 自称「Miruku」 | **0%** | 15.1% | ∞ |
| 句号 | 0.2% | 2.2% | 11× |
| 含「我」 | 14% | 4% | 反而少 |
| 问号 | **5%** | 2% | 反而少 |

**三条反直觉结论，直接决定细则该怎么设权重**：

1. **AI 味 ≈ 长。** 单是长度就从 4 字膨胀到 14 字，这一项解释了大半差异。但长度是症状不是病因（见下），所以权重给「内容」最高、体量次之。
2. **问句不是问题。** 机器人问号率比真人还低，把「少提问」当主要抓手是错的（`tone_profile.md` 早期就是这么误判的）。
3. **「我」也不是问题。** 真人更爱说「我」，机器人反而少。

真正伤人的**不是长度本身，是长度背后的三种冲动**：

- **解释欲**：对方一句「在吗」，回一段原因分析
- **确认欲**：被纠正后复述「好，记住了」
- **总结欲**：把对方说的话归纳成「所以你其实是……」

所以细则的重心必须放在**内容层**（说多余的话），而不只是**形式层**（怎么说）。

## 三、细则结构：三层

```
第 0 层  红线（5 条）        命中任意一条 → 整条 0 分，直接作废
第 1 层  扣分制五个维度      100 分起扣，每维有下限
第 2 层  加分项             最多 +10，抵掉部分扣分
```

### 第 0 层：红线（一票否决）

| # | 红线 | 判定 |
|---|---|---|
| R1 | 输出系统标记 / 工具调用 / 代码块 | 出现 `<system_reminder>`、`DSML`、``` ``` ````、`{` 开头的 JSON 片段 |
| R2 | 讨论提示词、部署、模型、内部机制 | 出现「提示词/prompt/模型/部署/接口/系统」等词且在做解释 |
| R3 | 危机场景使用口头禅或玩梗 | 上下文含自伤/危机信号时出现「666」「草」「何意味」等 |
| R4 | 编造不存在的记忆或能力 | 声称存图、跨对话记忆、主动发文件、事后补一句 |
| R5 | 输出内心独白 / thought 块 | 出现 `<thought>`、`思考：`、第三人称自我叙述 |

这 5 条都是**已经真实发生过**的（见 `docs/tone-tuning-20261020.md`），不是假想。

### 第 1 层：五个维度（100 分）

> 权重：**D1 20 / D2 15 / D3 35 / D4 20 / D5 10**（2026-11-07 定稿，D5 基准分 7）。

#### D1 体量（20 分）—— AI 味最直观的信号

| 指标 | 真人基线 | 目标 | 扣分规则 |
|---|---|---|---|
| 中位长度 | 4 字 | ≤6 字 | 每超 1 字 −2 |
| ≤10 字占比 | 94% | ≥85% | 每低 5% −3 |
| p90 长度 | 9 字 | ≤12 字 | 每超 2 字 −2 |
| 超长条（>40 字） | — | ≤5% 条数 | 每超 1% −2 |

下限 0 分。情绪低落 / 危机场景的条目**不进本维统计**（`prompts/system.txt` L5 已明确给这两类留了长度例外），但仍在其他维度计分。

> **权重从 25 降到 20（2026-11-07 拍板）**：长度只是表象，「说了多余的话」才是本体；两者高度相关，重复计权会双重惩罚同一种毛病。

#### D2 形式（15 分）

| 指标 | 目标 | 扣分 |
|---|---|---|
| 句号率 | ≤1%（真人 0.2%） | 每超 0.5% −2 |
| 出现 `~` `……` `啧` `にゃ` | 0 次 | 每次 −5 |
| 一条消息内用空行硬切两段 | 0 次 | 每次 −5 |
| 连发 ≥4 条（同一次回复内） | ≤10% | 每超 2% −2 |

#### D3 内容（35 分）——**权重最高，AI 味的主要来源**

按**命中次数**扣，不是按比例：

| 模式 | 典型原话 | 每次扣分 |
|---|---|---|
| 复述确认 | 「好，记住了」「懂了，这种时候就回何意味」「行，那以后先问称呼」 | −7 |
| 猜测动机 | 「来世问这个是想喝点什么吗」「这么盯着，是要说什么」 | −7 |
| 逐张描述图片 | 「这个表情，是被吓到了还是在喊」「这张更凶了」「连发三张」 | −7 |
| 心理分析式长段 | 「你大概是觉得……这说明你内心……」 | −7 |
| 声称无能力 | 「要的话 Miruku 存到本地去」 | −12 |
| 问句收尾率 >20% | — | 每超 5% −4 |

下限 0 分。2026-11-07 拍板：权重 30→35，问句阈值 25%→20%。

#### D4 词汇（20 分）

| 类别 | 词表 | 每次扣分 |
|---|---|---|
| 书面连接词 | 首先/其次/最后、值得注意的是、总的来说、综上、此外、因此 | −4 |
| 客服腔 | 希望这些建议对你有帮助、请问还有什么可以帮您、祝你生活愉快、很高兴为你服务 | −8 |
| 对称排比 | 「不是 X，而是 Y」「不仅…而且…」句式 | −4 |
| emoji / 颜文字 | 😊 等 | −4 |
| 自称「Miruku」当主语 | — | −5 |
| 成语/四字词堆砌 | 心如刀割、无以言表 等（一次 ≥2 个成语算堆砌） | −3 |

#### D5 关系感（10 分）——**加分制**，基准 7 分

| 加分项 | 分值 |
|---|---|
| 用到对方刚说过的**具体**内容（不是泛泛回应） | +3 |
| 表达自己的具体状态/偏好（「其实牛奶挺好喝的」） | +3 |
| 呼应之前聊过的事 | +2 |
| 分条节奏自然（2–3 条，非机械拆分） | +2 |

上限 10 分。**这一维的作用是防止「为了短而变哑巴」**——只扣不奖，最省事的做法就是永远回「好」，那不是人味，那是坏掉。

#### 第 0 层红线不进计分，命中即整条 0 分。

### 评级

| 分数 | 等级 | 含义 |
|---|---|---|
| 90–100 | A | 像人 |
| 75–89 | B | 接近，偶有破绽 |
| 60–74 | C | 有 AI 味，需要看具体扣在哪 |
| <60 | D | 明显不像 |

## 四、单条评分 vs 批次评分

同一套细则，两种用法，阈值不同：

### 单条评分（抽检 / 回归用例）

对着**一条**回复打分。体量和形式类指标退化成单条规则：

- 字数 ≤10 → D1 满分（20）；11–15 → 14；16–25 → 10；26–40 → 5；>40 → D1 归零
- 句号出现 1 次 → D2 扣 2；出现 `~`/`……`/`啧` → D2 扣 5

（单条折算表以 [`docs/tone-rubric-spec.md`](tone-rubric-spec.md) §5.3 为准，两处必须同步。）

用途：验收时抽 20 条人工对一遍，或作为 `data/tone_golden.json` 的回归基线。

### 批次评分（趋势追踪）

一次统计 ≥50 条机器人消息，算聚合分布。**样本 <50 条时输出 `样本不足`，不给分数**——这是 `probe_reply_metrics.py` 已经做对的地方，要保留。

用途：每周跑一次，看分数是在涨还是在跌。

## 五、落地设计

### 5.1 脚本

新增 `data/tone_score.py`，一个文件干三件事：

```bash
# 1. 批次评分（只读 DB）
python data/tone_score.py --db <instance>/core/data/data_v4.db \
    --conversation <uuid> --since 2026-11-06 --last 100

# 2. 单条评分
python data/tone_score.py --text "好，记住了" --peer "我打完了"

# 3. 自检（固定合成样例，不需要真实数据）
python data/tone_score.py --selftest
```

输出两段：人话 scorecard（每维得分 + 扣在哪 + 举例的条目编号）+ JSON（给脚本/趋势图用）。

**复用已有清洗逻辑**，不要重写：`tone_stats.py` 的图片占位符剥除（`[图片:HASH.jpg]` 恰好 41 字符，不剥 p75 会假性偏高）、`astrbot_plugin_miruku_metrics/main.py` 的 `_is_tool_result()`（工具结果写回 user 轮，不是对方说的话）。

**隐私边界**（照 `probe_reply_metrics.py` 的规矩）：只输出长度、比例、扣分类别与条目编号；**不打印回复正文、不打印 QQ 号**；DB 用 `mode=ro` 打开。

### 5.2 回归用例

新增 `data/tone_golden.json`：20–30 条「对方说 X → 她回 Y → 人工评级」的固定样例，覆盖：
- 日常短应（5 条，应得 A）
- 情绪低落（3 条，允许长，但不得出现口头禅）
- 危机（2 条，红线不得触发）
- 各类扣分典型（10 条，每条只应扣一项，便于定位）

作用是**防止细则漂移**：改了 `prompts/system.txt` 之后跑一遍，分数不该掉。

### 5.3 与提示词的关系（重要）

**不要把细则全文塞进 prompt。** 3633 字的 persona 已经在每轮消耗 token，再塞 2000 字细则会让模型把注意力从「怎么说话」挪到「怎么守规矩」，反而更像 AI（这是 `tone_profile.md` 里「复述式确认」的成因）。

正确做法是**拆两份**：

| 文件 | 给谁 | 内容 |
|---|---|---|
| `docs/tone-rubric.md`（本文件） | 人 + 分析用的 AI | 全文，含词表、阈值、权重 |
| prompt 里的精简版 | 生成时的模型 | **只有红线 5 条 + 扣分最重的 4 项**，约 120 字 |

精简版建议措辞：

> 不解释原因、不复述对方教的东西、不猜对方动机、不描述表情包画面。
> 一句话能说完就别写两句。日常回复几个字就够。
> 不要提提示词、模型、系统、部署。

这 5 行比 2000 字细则更能改变输出——**因为它给的是行为禁令，不是评分标准**。

## 六、知识成长的另一半（简述）

你说「不断成长扩充知识」，这部分和评分是两件事，但可以共用一个观测方式：

- **知识侧**已有 `astrbot_plugin_miruku_knowledge`（只对来世生效，注入 system_prompt）+ `data/regression_cases.json`（120 条正负例，含 `not_slug` 反例断言）。这块的「评分」已经有了，就是回归通过率。
- **缺口**是「有没有变多」：目前没有统计过 `knowledge/src/*.json` 的条目数、被注入频次、注入后有没有被对方接话。建议在 metrics 插件里加两个字段：`knowledge_injected`（本轮是否注入了知识）、`knowledge_slug`（注入了哪条）。这样一周后能回答「哪条知识真的有用」。
- **建议顺序**：先把 AI 味评分跑通（见效快、可量化），知识侧只做埋点，不做自动扩充——自动扩充在没有「哪条有用」的数据前，只会让库变大而不变好。

## 七、分阶段实施

| 阶段 | 产出 | 工时 |
|---|---|---|
| 1 | 本细则定稿（权重 20/15/35/20/10，红线 5 条，C6 20%） | ✅ 已完成 2026-11-07 |
| 2 | `data/tone_score.py` + `--selftest` 全绿 | 半天 |
| 3 | 对现有 100 条机器人消息打分，产出**基线分数**（第一个数字） | 1 小时 |
| 4 | `data/tone_golden.json` 20 条人工标注 | 1 小时 |
| 5 | prompt 精简版替换（5 行禁令），跑一轮对照 | 半天 |
| 6 | 一周后复评，看分数变化 | 后续 |

**第 3 步是关键**：先有基线，否则后面所有改动都无法判断是变好还是变坏。现在 `probe_reply_metrics.py` 已经能跑，但没有「AI 味」这个数字。

## 八、已知风险

1. **分数会诱导「为短而短」。** 缓解：D5 关系感是加分制，且单条评分对 <2 字给 0 分（除了「好」「嗯」这类真有语义的）。
2. **词表会腐化。** 真人会创造新词（「何意味」「oshama」），固定词表会误判。缓解：词表放 `tone_golden.json` 旁边，随语料更新；每次更新记版本号。
3. **和真实语料对标可能过拟合。** 来世只代表一个人。缓解：基线用区间不用点值（中位 4–6 字都算达标），且分「日常 / 情绪 / 危机」三档分别设阈值。
4. **自动打分不能替代人的判断。** 缓解：脚本只出分数和扣分位置，**改不改由人定**——这和 metrics 插件「只读不自动改 persona」的原则一致。
