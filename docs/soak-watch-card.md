# 24 小时试运行值守卡（WB-11）

> **给"守的人"用，不是给机器用。** 它不监控、不改任何东西，只规定五件事：
> 什么时刻才算**开始**计时、每天看哪**三处原始量**、看到什么必须**归零**、**发现后**几分钟内通知谁、收工时**交什么**给 Codex。
>
> 判据不在这里：证据分层见 `docs/pilot-go-no-go.md` §A-2，归零见 §A-3，数值在 `data/probe_uptime.py`。
> **本卡只执行，不允许重新解释判据。** 它是**日检**，不是实时告警（§4）。全程与来世无关——不需要他发一个字，也不许拿他的会话当样本。
>
> **⚠️ 2026-10-24 变更（OTTO 决议 D4）**：**本卡不再是放行闸**。放行闸改为「**崩了能自己起来**」的自愈验证（杀进程 → 自动恢复 → 被动可回 → 心跳 ≤10min → 连续 3 次 3/3 → 主动侧行为显式记 → **空窗消息可补性有结论**，共七项，见 `docs/otto-decisions-20261024.md` D4）；本卡降级为**观察期记录卡**，用来发现"她其实一直没连上""重启过几次"这类问题。**卡内判据一字不改**，只是用途从"判放行"变"记观察"。
>
> **观察期顺手记一条（不新增动作，只多写一行）**：哪天看到"某条消息他没回"，别当成他不想说——先看那一刻有没有重启／重连记录。**这属于 D4 第 7 条的现场样本**，比人工造测试更真实；记进备注列即可。

## §0 三句话

1. **载体没定，计时不许开始。** 现在这台 Windows 桌面实例只是临时验证环境，在它上面跑满 24 小时**不作数**（换设备要重装重扫码、探针路径全改）。本卡真正生效的第一天，是**迁移完成、新载体上第一次干净启动**那天。
2. **心跳没落地之前，跑到底也不会得到"可放行"。** 没有周期心跳时，**进程死掉／QQ 掉线／插件崩掉三种故障在数据上完全同形——都是"什么都没有"**。探针最多到 `UNPROVEN`：这是结构性的，多等两天不会变。
3. **只干四件事**：开表（§1）／每天一分钟（§3）／归零通知（§4）／交证（§5）。**跑偏的典型就是擅自"优化"判据**——那等于改结论。

按 §3 表格填第一行；**E1–E5 缺一条，就不许在那行写「开始」**。写不出来的格子写「未知」，**不许写"大概""应该是"**。

| # | 必须具备 | 怎么看见（只读） | 拿不到时 |
|---|---|---|---|
| E1 | **载体已定且已迁移** | 表头写设备型号＋实例目录；必须与最终投放同一台 | **不计时**（§A-0） |
| E2 | **心跳已落地并实测** | `grep -c "<心跳标记>" logs/astrbot-*.log` 有值且**跨 ≥30 分钟还在增长**；标记同时填进 `HEARTBEAT_MARKS` | **不计时**；空跑到 `UNPROVEN` 等于白跑 |
| E3 | **一次干净启动** | 日志出现 `core.main:144`，据此记**起跑时刻** | 没有起跑时刻＝没有起点 |
| E4 | **恰好一次链路事件** | 同段 `aiocqhttp_platform_adapter:107` 出现 **1 次** | 出现 2 次＝**本段作废**。探针按 `core.main:144` 切段，**第二次连接不会自动生成新段**——必须重新干净启动（或单独取证恢复时刻）才有新起点，「从第二次之后重算」不成立 |
| E5 | **收件口径已定**（甲／乙） | **已定＝乙**（OTTO 决议 D5）：临时把观察库 `target_qq` 指向测试号，验一次真实往返；**改前记原值、改回后立刻读运行配置核对、24h 内确认来世消息已入库** | 防呆三条见 `docs/otto-decisions-20261024.md` D5；少一条就退回甲，并在表里写明"本次只验进程与连接" |

> **E2 是命门。** 实例里**没有任何一处**周期性写"我还活着＋适配器在线"：观察插件的轮询（`_poll_history` → `_sync_history`）每 10 秒醒一次，但**没新消息时 `_sync_history` 直接 `return`，既不写库也不打日志**。
> 于是"库里最后一条是早上"和"插件已经崩了六小时"长得一模一样。定位用 `grep -n "_poll_history\|_sync_history" <observer>/main.py`，**别记行号**（每改必漂）。

## §2 四种"活着"必须分开写（本卡最容易错的地方）

| 你看到的 | 证据长什么样 | 证明了 | **不能**推出 |
|---|---|---|---|
| **① 进程活着** | 本段出现过 `core.main:144` | 程序启动过 | 连过 QQ；能回话；之后还在跑 |
| **② QQ 连上过** | `适配器已连接` 出现 **1 次** | 某一刻连上过 | 之后一直在（**再出现一次就是断过**） |
| **③ 此刻仍在线** | 周期心跳行，空档 ≤10 分钟 | 一直在线 | 能收发业务消息 |
| **④ 测试号往返成功** | **机器人回复气泡**（Miruku 那条）＋ 日志中该条消息行 | 这条链路真的通了 | 24 小时不宕；对来世也对 |

**四条硬规矩**：② 不能当 ③ 用（拿链路事件当在线，结果是**断得越多越像健康**，WB-10 v3 已踩过一次）；③ 不能当 ④ 用（一直在线也可能收到不回）；**④ 只认气泡**——观察库多一行只证明**入站被看见**，不证明**回复发出**（C-09 未修前记录可能比气泡多）；**不许拿一次事件替代连续**。

## §3 每天一分钟（照抄，不要发挥）

```bash
PY="C:/Users/OTTO/.astrbot_launcher/instances/298681be-6ba8-4137-818c-28ed67ec9176/venv/Scripts/python.exe"
$PY data/probe_uptime.py                      # 【二】当前段原始量（要看）＋【三】历史最长段（不许抄）
$PY data/probe_uptime_selftest.py | tail -2   # 30 项样例：分清是判据坏了还是你看错了
```

**只看【二】，不看【三】。** `probe_uptime.py` 的【三】取的是 `max(segs, key=duration)`——**历史最长启动段**，不是当前段。将来某个历史段一旦够到 `PROVEN`，即使今天已经重启或掉线，【三】照样显示 `PROVEN`。**把【三】抄进表＝用旧成绩当今天的成绩。**

每天按这个顺序看（顺序就是判据）：

| 步 | 看哪里 | 读到什么 |
|---|---|---|
| 1 | 【二】`当前所在启动段起点` | **这一行就是段起点**；没有这一行＝进程已停（看【一】最后一行） |
| 2 | 【二】`该段链路事件 = N 次` | `0`／`1`／`≥2` |
| 3 | 【二】`心跳 = N 拍` ＋ `最长无心跳空档` | 拍数 0 或空档 >10min |

**当天档位由值守人按上表手工推，不许从【三】抄**：

| 当天档位 | 推法 | 该做什么 |
|---|---|---|
| `NOT_REACHED` | 段长 <24h（现在 − 段起点），或链路事件 = 0 | 继续跑；段起点是今天＝计时刚被打断 |
| `BROKEN` | 链路事件 ≥2，或见掉线事件 | 当天归零＋通知（§4-P1）；**探针不会把重连处自动切成新段**，须重新干净启动 |
| `UNPROVEN` | 段长够、链路 1 次、无掉线，但心跳 0 拍或空档 >10min | **不是即将通过**，是缺心跳，别等 |
| **无当前段** | 【二】没有"当前所在启动段"那行 | 进程已停＝计时中断，按 §4-P1 |

`PROVEN` **不接受自行宣布**：必须 Codex 对**当前段**重新判定后才成立（探针补"当前段判定"也由 Codex 负责）。

**计时表（一行一天，只这 7 列，不许加"体感评分"列）**

| 日期 | 段起点 | 链路事件次数 | 心跳最后时刻 | 当天档位 | 检测延迟 | 动过设备吗 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

**五件事都要反着读**（连接次数上涨＝断了几次／"今日启动 0 次"在跨午夜段天然是 0／日志无报错＝只是没炸／观察库不涨＝可能入站已停／"她没主动"＝主动本就停摆），十条见附录 C。

## §4 归零与通知（谁、何时、说什么）

**先说清一件事：本卡是日检，不是实时告警。** 两个时钟必须分开记：

| 时钟 | 含义 | 怎么得到 |
|---|---|---|
| **T_e 事件时刻** | 掉线／重启／心跳停下**发生**的时刻 | 日志行自带的时间戳 |
| **T_d 发现时刻** | 值守人跑命令**看到**它的时刻 | 跑 §3 命令的时刻 |
| **T_n 通知时刻** | 发出通知的时刻 | 只对 T_d 有承诺 |

**唯一承诺：`T_n − T_d ≤ 10 分钟`（发现后 10 分钟内记录并通知）。`T_e → T_d` 一律如实写成「检测延迟」**，不许抹掉——日检的检测延迟上限≈检查间隔，可能接近 24 小时。
**若要"故障发生后 10 分钟内就知道"，只能靠自动监测**；本项目目前没有（C-17 告警链路零实现、无 alert 插件，且 **OTTO 2026-10-24 决议 D1 已书面接受不实现**，见 `docs/otto-decisions-20261024.md`），所以本卡不承诺，也不许对外写成"已监控"。

**归零只有三条**（任一发生，本段作废，从 0 重算，**没有"这次不算"**）：① 新的 `core.main:144`（含系统更新／断电／手动重启）；② 段内**第二次** `适配器已连接`；③ NapCat `账号状态变更为离线`／`KickedOffLine`／`登录已失效`。

**发现后 10 分钟内做两件事**：① 计时表当天写「归零＋原因＋证据行原文＋T_e／T_d／检测延迟」；② 按下面分级通知。

| 级别 | 触发（在巡检时看到） | 通知谁／何时 |
|---|---|---|
| **P1 当天** | 段被归零／无当前段／掉线事件／**心跳最后时刻已停超 30 分钟** | 通知 OTTO，一句话：「24h 计时于 X 月 X 日 X:XX 归零，原因 <重启/重连/掉线>，证据 <日志行>，发现于 X:XX（延迟 Xh）」 |
| **P2 次日合并** | 连续两天 `UNPROVEN` 且心跳为空 | 通知 OTTO：「现在不是等时间，是缺心跳；再等也不会变」 |
| **不通知** | 正常增长、正常跨午夜、正常无消息 | 只记表 |

**谁记录**：当班值守人（默认 OTTO）。可委托 Codex **代跑两条命令并回传原始输出**，但「拍板」和「通知」仍在 OTTO。**WorkBuddy 不参与运行侧值守**，也不替任何一方判断达标。

**值守期间禁止**：为"跑得更干净"夜里手动重启；把维护窗口从计时里摘掉或标"不算"；拿"折腾了一整天"替代 24 小时；让来世配合试跑、给他发测试消息、或用他的真实会话当样本。

## 附录 C 常见误读（每条都在本项目真实发生过或差点发生）

1. 「连接了 4 次，说明在线很稳」→ **反了**，这是断了 3 次。
2. 「扫码成功了，就说明在线了」→ 扫码 ≠ 登录成功 ≠ 适配器可用。
3. 「观察库有新行，说明她能回话」→ 只证明入站被看见。
4. 「日志没报错，应该没事」→ 三种故障都不报错。
5. 「今日启动 0 次，是不是没跑」→ 跨午夜连续运行时这就是正确的 0。
6. 「今天没主动，她挺克制的」→ 主动排期是停摆态（C-10）。
7. 「设备没重启，所以 24 小时成立」→ 探针只读日志，只读侧证明不了没写下来的时段。
8. 「`group_chat_plus` 里有 `heartbeat` 字段，可以拿来当心跳」→ **不行**。那是**浏览器面板的会话心跳**，只在有人开着网页、按请求刷新时才跳；没人看面板它就不跳。把 `HEARTBEAT_MARKS` 指过去，等于"我开着面板的时段才算在线"——最隐蔽的一种假证据。
9. 「跑了 3 天，累计 26 小时」→ 累计无意义，只认单段。
10. 「这次因为维护重启，不算」→ 这句是所有计时失效的起点，写死禁止。
11. 「探针【三】写着 `PROVEN`，今天可以收工」→ **不行**。【三】判的是 `max(segs, duration)`＝**历史最长段**，可能是上周那一段；今天重启过、掉线过它也不会变。收工只认 Codex 对**当前段**的复核。
12. 「掉线后从第二次连接往后重新算」→ 探针按 `core.main:144` 切段，重连**不会**自动生成新段，那一段始终是 `BROKEN`。要么重新干净启动，要么单独取证恢复时刻。
13. 「夜里掉了线，我第二天早上发现，也算 10 分钟内通知到位」→ 不算。承诺的是**发现后 10 分钟**，`T_e → T_d` 那段要被写成「检测延迟」，不能抹掉。
