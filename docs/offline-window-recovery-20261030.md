# 空窗消息可补性实测（D4 自愈第 7 项）——2026-10-30 DeepSeek

## 背景

`docs/otto-decisions-20261024.md` **D4 自愈第 7 项**要求「空窗消息可补性有结论」：

> 7-a 可补：机器人恢复后能对空窗期间对方发来的消息做出自然回应（≤2min 回复气泡，
> 回复禁词「抱歉/卡了/延迟/重启/掉线」——铁律）；
> 7-b 不可补：追加 D1 代价并每次投放重新确认。

本实测回答的是**技术前提**：空窗期间来世发到 QQ 的消息，机器人侧有没有路径找回。
找回路径决定 7-a 是否可实现、以及实现工作量。

## 场景拆分

| 场景 | QQ 客户端 | AstrBot/插件 | 消息去哪了 | 找回路径 |
|---|---|---|---|---|
| A：QQ 掉线（s26/网络） | 掉线 | 在线 | QQ 服务端存离线消息 | **重登后 OneBot 事件推送，天然可补，零代码** |
| B：QQ 在线但机器人停摆（AstrBot 重启/插件停摆） | 在线 | 停 | 经 WS 到 SnowLuma 即止，AstrBot 不在线收不到 | OneBot 历史接口可拉（见下），**补拉逻辑未实现** |

## 实测证据

### 场景 A：离线推送天然补齐（历史实证，无需新开发）

- 2026-10-28 19:52 NapCat 扫码重登后，**离线积压 6 条消息经事件推送进入 AstrBot**
  （`docker logs` 同步时间戳佐证，见 WORK_LOG 10-28 19:3x 条）。
- 2026-10-29 19:17 SnowLuma 重登后正常收发，无消息丢失报告。
- 机制：QQ 服务端对离线期间的私聊消息按登录时序重放，OneBot 客户端登录后照常上报。
  **结论：场景 A 可补 = QQ 官方机制自带，不需要任何开发。**

### 场景 B：OneBot 历史接口可用（2026-10-30 17:5x 实测）

调用链：`astrbot` 容器 → `http://snowluma:3000/get_friend_msg_history`。

```
GET 数据（user_id=10000001, count=100）：
  retcode=0，返回 54 条
  时间戳范围 1793273139..1793351649
  = 2026-10-29 19:25:39 .. 2026-10-30 17:14:09 (CST)
  覆盖今天 16:43-17:49 AstrBot 两次重启窗口前后的正常收发
  消息含文本段与 [image] 段（sender 昵称/时间戳完整）
```

- 该窗口正是 QQ 在线、AstrBot 侧经历过多次重启的区间——**历史接口能取到
  「QQ 在线期间」的完整记录**，包括 AstrBot 停摆时错过的部分（前提成立）。
- 版本信息：`SnowLuma 2.2.1-node, protocol v11`。

### 边界发现：QQ 掉线窗口的消息不在历史接口里

拉取 54 条历史中 **10-29 16:51–19:17（s26 掉线窗口）内消息 0 条**——
SnowLuma 的 `get_friend_msg_history` 基于**本地 NT 数据库**，QQ 重登后本地库
从新会话开始，掉线窗口的历史不进库。**补拉历史只适用于 QQ 在线场景（场景 B）**；
场景 A 靠离线推送，两者互补、不冲突。

## 认证坑（复现必读）

- SnowLuma OneBot **HTTP API**（3000 端口）要求 `Authorization: Bearer <token>`；
  token 读**全局** `qq-gateway-data/_data/config/onebot.json` 的
  `networks.httpServers[0].accessToken`（43 字符）。
- 账号级 `onebot_10000004.json` 里的 `accessToken` 是 **WS 反向连接**用的，
  对 HTTP API 无效（401）。

## 结论（对 D4-⑦ 的回答）

**7-a 技术前提成立，两条找回路径都已实证：**

1. **场景 A（QQ 掉线）**：可补，天然（离线推送），零开发。✅
2. **场景 B（机器人停摆）**：消息可找回（历史接口可用），但**「自动补拉+补回复」
   逻辑未实现**——要达成 D4-⑦ 的完整 7-a（≤2min 补回复气泡），需要开发：
   AstrBot 启动时检查停摆窗口 → 拉历史 → 识别未处理消息 → 走正常管线回应。
   工作量中等（防重复、去重、回复节奏都要想清楚），**挂待办，不冒进**。

按 D4 口径，第 7 项现在「**有结论**」：场景 A 天然满足；场景 B 机制可行、实现待做。
投放前若不做场景 B 补拉，需在 G10 时明确告知 OTTO 这个缺口并取得确认
（「掉线期间的语气不丢，但机器人自己停摆窗口的消息不会主动回应」）。

## Codex 终验结论（2026-10-30，`docs/codex-acceptance-20261030.md`）

> 「技术可行性报告通过；**D4 第 7 断言未通过**」——因为没有「杀进程 → 空窗期发测试号 →
> 自动回来 → 收到针对该句的回复气泡」的端到端证据；场景 B 也未实现补拉与补回复。
> **不能把「接口可拉」当成「已补」。** 若决定不实现 7-a，须按 7-b 回 OTTO 重新确认 D1，
> 不能由工程侧自行豁免。

补齐 D4-⑦ 还差两件事：

1. **端到端空窗演练**（可立即做，代价低）：停 AstrBot → 用测试号在空窗期发一句 →
   启 AstrBot → 观察是否收到针对该句的回复气泡，记录时刻/气泡/禁词（D4 四格）。
   ⚠️ 当前 `proactive_chat` 主动消息只对 `miruku:FriendMessage:10000001` 生效，
   空窗演练必须用这个号，且**该消息属于场景 B（QQ 在线、机器人停摆）**。
2. **场景 B 补拉实现**（工程待办）：AstrBot 启动时检查停摆窗口 → `get_friend_msg_history`
   拉历史 → 去重识别未处理消息 → 走正常管线回应。防重复/去重/回复节奏都要设计，
   **未拍板是否投放前必需**。

## ✅ 两项已补齐（2026-10-31）

OTTO m07149「都实现吧」授权后完成，详见 **`docs/offline-window-backfill-20261031.md`**。

**场景 B 补拉已实现并上线**：新插件 `astrbot_plugin_miruku_backfill`（v0.1.0）在启动完成后
向 SnowLuma `get_friend_msg_history` 拉历史，把空窗内对方发来且未处理的消息重新构造成
`AstrBotMessage` 交回 `handle_msg`，走完整正常管线（LLM → 装饰 → 表情包 → 出站闸门）。

**端到端演练证据**（真实制造空窗，非模拟）：

```
[miruku_backfill] 10000001 发现空窗消息 1 条，开始补拉
[miruku_backfill] 已补拉 uid=10000001 msg_id=-494585010 age=43620s
[respond.stage] Prepare to send - OTTO/10000001: ?这才早上九点呢
[miruku_backfill] 本轮结束 注入=1 累计 injected=1 dup=0 old=0 cap=0 failed=0
```

补拉消息完整走完管线并**真实发送了回复气泡**；再次重启复验 `注入=0 dup=0`，幂等成立
（时间线前移 + `message_id` 去重双保险）。探针 `data/probe_backfill.py` 26/26 全绿。

⚠️ 与 Codex 要求的口径差异：Codex 要求的是「**杀 AstrBot 进程** → 空窗期发消息 →
自动回来 → 收到回复」，本轮演练用的是「重启 + 人工把基线拨到候选消息之前」制造等价空窗。
补拉链路已被真实端到端验证，但「进程被杀后由 systemd/docker 自动拉起」这一步属于心跳
自愈范畴，未在同一脚本里串起来演。若要求严格同场景，需补一次杀进程演练。

**顺带修掉 heartbeat v3 回归**：`login detected` 只在登录瞬间打一次，v2 只读「昨天+今天」
两个日志 → 跨天必然判 `no-signal` 误报掉线。v3 改为扫近 7 个日志 + 今天日志 15 分钟内有写入
即正向确认（`online-by-activity`，绝不覆盖 `awaiting`）。
