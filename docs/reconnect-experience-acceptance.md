## 零、先给结论

**五条，前两条改了现有设计的假设，后三条是必须让 OTTO 知道的取舍。**

1. **"未送达"目前会被记成"已送达"的情形只有一种，但它是真实存在的**：分段投递时只要**任意一段**成功，`send_proactive_message` 就返回成功（`sender_service.py` L467 docstring、L519 `any_sent`、L552–557 逐段累加），随后 `flow_orchestrator.py` L219–225 把未回复计数 +1、L191–196 把**整段全文**写进对话历史。QQ 端只有第 1 条气泡，记录里是完整故事。**这和 `crisis-alert.md` §三 已经废除的"任一层成功即算送达"是同一个错误形状**，只是发生在陪伴消息上。

2. **停机跨过预定触发时刻超过 60 秒后，主动消息会静默停摆，直到来世先开口。** 依据：`is_persisted_task_still_valid`（`scheduler_service.py` L157）有效条件为 `now < next_trigger + 60`；超时则 `init_jobs_from_data` 清理状态不恢复；而运行配置 `auto_trigger_settings.enable_auto_trigger = false`（2026-10-22 只读实测），`setup_auto_trigger_for_session_config` L421 直接返回 `"disabled"`——**没有第二条重新上膛的路径**。私聊里唯一的重排入口是 `event_handlers.py` 的 `on_friend_message` 末尾 `schedule_next_chat_and_save(reset_counter=True)`（L161–166）。**夜间关机 8 小时必然跨过这个窗口**。

3. **断线期间到期的消息不会被补发，而是被丢弃后重排到 180–360 分钟之后。** 发送失败 → `DeliverStage.handle`（`features/deliver/split_delivery.py` L30–44）`ctx.abort("send_failed")` + `RESCHEDULE` → `_on_reschedule`（`flow_orchestrator.py` L51–53）调 `schedule_next_chat_and_save()`，按 `min/max_interval_minutes = 180/360` 重算下一次。**内容不保留、不重试、不进队列。** 对陪伴是好事（不显得催促），对"故事续段"是坏事（续段消失且无人知道）。

   **但"不补发"不等于"没发生"**（v2 补充）：如果故事的**首段**已经在断线前出去，那么来世已经听到故事开头，**七日窗口照常被占用**（`story-opening-acceptance.md` §3.1 T0 = 首段出站成功）。续段作废只损失"后半句"，不退还"这一则故事的名额"。**把这两件事混成一个判据，就是 v1 §六-5 的错误。**

4. **"重连后补发"这件事，不建议做。** 对来世而言，机器人下线 8 小时和"她没说话"没有区别。任何"补一条""抱歉刚才没发出去""好久没联系了"都会把运维故障变成关系话题，让来世承担 OTTO 的运维成本。**恢复的正确形态是"从现在重新开始"，不是"把过去补上"。**（这条与危机告警相反：告警必须补，因为它的读者是 OTTO，不是来世。）

5. **对来世不可见 ≠ 对 OTTO 不可见。** 停摆必须让 OTTO 看见（日志/PENDING 明确写"主动消息链路已停摆，待对方下次发言后恢复"），但不能让来世看见。**这两条是同一个原则的两面：同一事实，对不同读者暴露不同层级。**

## 一、六层事实模型（本文件所有判据都基于它）

WB-06 任务单要求"明确候选生成、API 返回、QQ 端收到是不同事实"。把它们拆成六层，任何一行状态都必须落在其中**一层**，禁止跨层合并：

## 三、四路恢复边界（按收件人分开写，别混）

任务单要求"分别写普通主动消息、故事续段、A/B 告警的恢复边界"。

**共同点不是"都不补发"——A 档明确会补发三次。**（v1 原文如此，与本节表格自相矛盾，v2 更正。）准确的共同点只有一条：**四路都按"收件人"决定诚实标准，而不是按"基础设施"决定。** 对来世：失败就当没发生，绝不把故障变成话题。对 OTTO：失败必须留下痕迹，绝不把"没送到"说成"送到了"。

| 维度 | 普通主动消息 | 故事续段 | A 档告警 | B 档告警 |
|---|---|---|---|---|
| 收件人 | 来世 | 来世 | **OTTO** | **OTTO** |
| 未送达时是否重试 | **否**（`RESCHEDULE` 重排**新内容**，原句丢弃） | **否**（资格作废） | **是**（3 次：+15/+30/+45 分） | **否**（发一次，不补） |
| 跨重启是否恢复 | 未过期才恢复（60s 宽限） | 不恢复（窗口/续段状态未持久化） | **恢复**（§7.6-5，按 `resend_state`） | 不恢复 |
| 恢复后是否"补上原来那句" | **否**，重新生成 | 否 | **是**，同一 `occurrence_id` | 否 |
| **首段成功是否消耗故事窗口** | 不适用 | **是**（T0 = 首段 F3，见 S3） | 不适用 | 不适用 |
| 失败后是否计入打扰预算 | 否（未回复计数 **不 +1**） | 否 | 不适用 | **否**——`suppressed_push_count` 只数"被限流挡下"，传输失败用 `delivery.failed_reason` |
| 失败原因的落点 | 日志 `send_failed` | 同左 + `story_aborted_at` | `delivery.failed_reason` | `delivery.failed_reason`（**不污染限流计数**） |
| 是否允许告知收件人"刚才失败过" | **绝对禁止** | 绝对禁止 | **必须**（不然等于谎称已收到，且要标明"重启补发"） | 必须（PENDING 层） |
| 权威依据 | 本文 §二 | `story-opening-acceptance.md` §2.5/§3.1 | `crisis-alert.md` §三/§7.6/§8.1 | 同左 |

**一句话**：**给来世的消息，失败就当没发生；给 OTTO 的告警，失败必须留下痕迹。** 前者是陪伴，后者是责任，同一套基础设施要走两套诚实标准。

### 3.1 一个必须显式区分的对：`suppressed` ≠ `failed`

`crisis-alert.md` §8.1 的 `suppressed_push_count` 语义是**"B 档超过 4 条/24h，被限流主动挡下"**，§8.2 的搭车行原文也是「今日另有 N 条 B 档**因限流**未推送」。把"QQ 不通导致发送失败"记进这个字段，会产生两个后果：

1. **搭车行说谎**：OTTO 读到"因限流未推送"，实际是链路故障。他据此会以为"B 档太多已被限流"，而真相是"一条都没发出去"——**归因完全错位**，可能导致他把 B 档的敏感度过调低。
2. **`suppressed` 与 `failed` 的处置相反**：`suppressed` 是"本 24h 内不会再发"（`push_state = suppressed`），而 `failed` 是"已尝试、按规则不重试"（B 档）或"要继续重试"（A 档）。**用同一个字段装两种终态，工程实现一定会写错重试条件。**

**修法（需 Codex 落地，本文只提接口）**：

| 状态 | 触发 | 是否再尝试 | 计数 |
|---|---|---|---|
| `push_state = suppressed` | B 档 24h 已满 4 条，第 5 条起 | **否**（本 24h） | `suppressed_push_count += 1` |
| `push_state = failed_final` | B 档发送失败（QQ 不通 / 平台未接受） | **否**（已拍板"不补发"） | **不增**；`delivery.failed_reason = "transport"` |
| `push_state = pending` + `resend_state = active` | A 档发送失败 | **是**（+15/+30/+45） | 不适用 |

> `failed_final` 是新增终态。**不加它，B 档失败只能塞进 `pending`（违背"不补发"，会被调度器反复拾取）或塞进 `suppressed`（污染限流归因）——两条都错。** 这一条已登记为 C-11。

## 四、需要 OTTO 拍板的三项（**2026-10-24 三项已全部落定**，过程留档）

## 六、给 Codex 的实现要点（本文不动手）

1. **送达状态改成四级枚举，禁止布尔**：`attempted` / `platform_accepted` / `all_segments_accepted` / `partial`。`any_sent` 现在的语义是 `platform_accepted`，被当成 `all_segments_accepted` 用——**这是要修的那一处**（`sender_service.py` L519/L552–567/L599–603）。

   **每个状态驱动哪个后果（v2 新增，这是 §零-1 的真正修法）**：

   | 状态 | 未回复计数 | 对话历史 | 续段资格 | **七日窗口** |
   |---|---|---|---|---|
   | `attempted`（一段都没出去） | **不 +1** | 不写原文，只记失败 | 否 | **不动** |
   | `platform_accepted`（**瞬时态**：至少有 1 次 send 成功，还没逐段确认完） | **+1** | 写全文（这是 C-09 未修时的现实） | 暂记"待定"，逐段确认后落到 `partial` 或 `all_segments_accepted` | **写入** |
   | `partial`（**终态**：逐段确认 `0 < sent < planned`） | **+1** | 写全文 + `segment_count_sent=1/2` | **否**（缺的就是后半段，见 D2） | **写入** |
   | `all_segments_accepted` | **+1** | 写全文 | **是** | **写入** |

   **一句话：窗口与未回复计数认"有没有出去过"，续段认"整条出没出去"。** 三者的判据不同，不能共用一个布尔。
2. **部分送达必须独立记录**：`segment_count_sent` / `segment_count_planned` 两个字段，写进对话历史条目旁，不要拼进正文。
3. **停摆检测（S6）**：启动时若"存在过期任务 + `enable_auto_trigger=false`"，写一行显式状态（日志 + `PENDING.md` 或等价物），措辞固定为「主动消息链路已停摆（原因：任务过期且未启用自动触发器），待对方下次发言后恢复」。**不许静默**。
4. **不要在重启时补发普通消息**：`init_jobs_from_data` 已符合；**不要为了"看起来没断"而加补发逻辑**。这条明确写进代码注释，避免后人"优化"。
5. **故事侧（v2 更正）**：`last_story_sent_at` 在**首段 `platform_accepted`（F3）成立时**写入，与 `story-opening-acceptance.md` §3.1 的 T0 定义一致。**不要等 `all_segments_accepted`**——那会让"首段已发出去、后半段失败"的故事完全不占窗口，七天后又开一则新的，等于 7 天内讲了两则。`partial` 与 `all_segments_accepted` 只影响两件事：① 是否记 `segment_count_sent/planned`；② 续段资格是否成立。**不影响窗口。**
6. **告警侧不改**：A/B 的递送与确认一律以 `crisis-alert.md` 为准；本文只约束"恢复时不混层级"。特别禁止把 `recorded` 写成「OTTO 已收到」。
7. **观察插件**：`astrbot_event.py` L592–596 的 `OnAfterMessageSentEvent` 在**分段循环之后只派发一次**，所以观察插件每"一次主动消息"记一行（`miruku_observer/main.py` L125–127，无过滤）。**这意味着出站记录条数 ≠ QQ 气泡数**，验收一律以气泡数为准，别拿数据库行数当送达证据。
8. **幂等已具备**：`add_chat_job` 的固定 id + `replace_existing=True`（L254–267）保证重复连接不产生双任务。**新增任何"重连后重排"逻辑时，必须沿用这个 id 约定**，否则 S8 会破。

### 9.1 一处 Codex 未提、但由其第 ② 条引出的连带缺口（C-11）

把"发送失败"从 `suppressed_push_count` 剥离之后，**B 档失败在现有 `push_state` 枚举里没有合法位置**：

- 放 `pending` → `push_due_at` 到期会被调度器反复拾取，**违背已拍板的"不补发"**；
- 放 `suppressed` → 污染限流归因（正是第 ② 条要修的问题）；
- 放 `sent` → 直接说谎。

`crisis-alert.md` §「字段取值约束」里 `push_state` 只有 `pending` / `sent` / `suppressed` 三个值。**所以第 ② 条不是"改一句话"，它要求 `crisis-alert.md` 侧新增一个终态。** 已登记 `docs/defect-register.md` §C-11，请 Codex 在实现 A/B 链路时一并定值（建议 `failed_final`，并由 `delivery.failed_reason` 携带原因）。

**这条会卡在 A/B 链路实现前**：如果先写代码再补状态，B 档失败几乎必然被塞进 `pending`（最省事），而"发一次、不补发"会因此变成"无限重试"——**恰好是 OTTO 拍板时明确否掉的那个行为。**
