# 危机 / 袒露之后的关怀消息规范

> 决策来源：OTTO 于 2026-10-21 决定——危机或袒露之后，下一条自动发出的消息改为关怀确认（如"你还好吗"），而不是照常抛轻话题。
> **2026-10-21 追加决定**：即使是 A 档（明确自伤意图）**也必须发**，不静默；发什么由 WorkBuddy 定，本文件第三节即为定稿。
> 本文件是该决定的落地规范。撰写：WorkBuddy 智能设计助手。日期：2026-10-21。
> **2026-10-21 v3（WB-03R 第 4 项）**：把 §3 里"不重发不追问"与"补问一次"两条读起来打架的规则，
> 合并为**单一计数器 `safety_ask_count`（上限 2）+ 两个固定槽位**；`inline_asked` 布尔已废弃。
> 另把"对话侧计数"与"告警侧 `ack_state`"明确切开：**两者不互相推导**。
> 边界：只写规范，未改 `configure_proactive.py`、`prompts/system.txt`、`persona/` 或运行配置，未向任何 QQ 发消息。

---

## 一、这个决定解决了什么，以及它同时打开了什么风险

**解决的**：现在调度器完全不看上一轮情绪状态，3–6 小时后照常触发。对方刚说完自伤意图，下一条是"今天打舞萌没"——这是不可逆的伤害。OTTO 的判断是对的，必须改。

**同时打开的风险（三条，每条都会让好事变坏）**：

1. **它会重新打开那一刻。** 对一个极少袒露的人，"你还好吗"等于提醒他"你昨天在我面前脆弱过"。有些人需要的不是被特别关照，而是**被正常对待**。所以关怀消息不能占满整条、也不能反复出现。
2. **它会把陪伴变成监护。** 一次是关心，每次都问就成了"我一直在盯着你的状态"。这比冷场更伤人。
3. **它可能被系统当成"危机已处理"。** 一条安慰话糊过去，真实的危险反而没人管。关怀消息**不能替代**现有的三步行动建议。

所以下面所有规则的目的只有一个：**让这条消息像朋友，不像监测系统。**

## 二、先分三档，不能混（这是最容易做错的地方）

| 触发状态 | 判定依据 | 下一条主动消息应对 |
|---|---|---|
| **A. 危机（自伤/自杀意图）** | 对方明确表达伤害自己的意图 | **必发，但只发一句：**「你现在安全吗？」。不抛轻话题、不用表情包、不讲故事、不做安慰式展开、不问第二个问题。 |
| **B. 袒露 / 低落（非自伤）** | "[自我否定类表达]""[欲言又止类表达]""好累""[关系愧疚类表达]" | **下一条主动消息改为关怀确认**（四句模板任选），之后恢复正常。 |
| **C. 普通** | 其余一切 | 按原 `proactive_prompt` 正常发。 |

**A 档为什么不能照 B 档办**：B 档是"接住情绪"，A 档是"确认安全"。用"你还好吗"处理 A 档，等于把急性风险降级成一个心情问题——而如果对方此刻真的处在危险里，"还好吗"这四个字换不来任何可行动的信息。

## 三、A 档定稿：「你现在安全吗？」

OTTO 已授权由我定这一句。定稿为 **「你现在安全吗？」**，不加任何前后缀。

### 为什么是这一句，而不是"你还好吗"

| 候选 | 判断 | 理由 |
|---|---|---|
| 「你现在安全吗？」 | **采用** | 唯一能拿到"是否仍处于危险"这个信息的问题；且它明确传递"你昨天说的那句，我没有当成没发生"。 |
| 「你还好吗」 | 不用于 A 档 | 太软。对一个刚说过想伤害自己的人，"还好吗"读起来像"我们把那件事翻篇吧"——这恰恰是最伤人的那种轻。 |
| 「在的话吱一声」 | 不用于 A 档 | 友好但零信息量。如果对方正处在危险里，收到这句只会得到"在"，然后呢？ |
| 安全确认 + 三步行动一起发 | 不采用 | 对方还没回话就先给一份行动清单，是**在沉默里对着空气说教**。三步行动要等对方回应、确认有风险之后再给。 |

### 关键的设计取舍（必须写进注释，防止后人改坏）

**"你现在安全吗"读起来比"你还好吗"重，这是故意的。** 两个方向的错误代价不对称：

- 发得太重，而对方其实已经缓过来了 → 他回一句"没事"，最多一点尴尬，**可撤回**；
- 发得太轻，而对方仍在危险里 → 这可能是唯一一次把他拉住的机会，**不可撤回**。

所以这一档宁可重，不可轻。

### 后续链条（严格三步，不多不少）

> **2026-10-21 修订（WB-03）：先分清两层，否则会出"同一句话问两次"的岔子。**
>
> | 层 | 时机 | 依据 |
> |---|---|---|
> | **即时层** | 对方刚说完，**当前对话内**，走普通回复 | `system.txt` L21 |
> | **后续层** | 3–6 小时后，走**主动消息** | 本节 |
>
> 本节的"三步"说的是**后续层**。即时层不受本节约束——对方说话时必须立刻回，不能等到 3 小时后。
>
> **两层互斥规则（2026-10-21 v3 改为单一计数器，WB-03R 第 4 项）**
>
> ~~v2 用 `inline_asked` 布尔 + 三条文字规则~~ ← **读起来仍像两条打架的规则**：
> 第 3 步写"对方不回复 → 不重发、不追问"，本段又写"没回应 → 补问一次"。
> v3 把次数**固定成两个槽位**，歧义就消失了：
>
> | 槽位 | 时机 | 触发条件 |
> |---|---|---|
> | **#1** | 即时层：对方刚说完，当前对话内 | 当时有回话机会就用掉（`system.txt` L21） |
> | **#2** | 后续层：下一条主动消息 | **仅当 #1 已用掉且未获任何回应**；若 #1 没用掉，则 #2 顶替 #1 |
>
> 单一计数器 `safety_ask_count`，上限 **2**：
>
> - #1 用掉、对方**有回应**（无论答什么）→ #2 **作废**，`safety_ask_count = 1`。72h hold 仍生效（不发轻话题）。
> - #1 用掉、对方**没回应** → #2 补问一次，`safety_ask_count = 2` → **此后永不再问**。
> - #1 **没用掉**（离线到达、当时无对话窗口）→ #2 问一次，`safety_ask_count = 1` → 此后永不再问。
> - **不存在槽位 #3。**
>
> **所以第 3 步"不重发、不追问"与"补问一次"是同一件事的两面**：
> "补问一次"就是那唯一的 #2；"不重发"指的是 **#2 之后永无第三次**。
> 之前两条规则看着矛盾，只是因为没写清次数归属——现在用槽位钉死。
>
> **这是否属于 OTTO 已授权的后续主动确认？是。** OTTO 于 2026-10-21 拍板
> "A 档必须发，且只发「你现在安全吗？」一句"，#2 就是那一次，
> **不是**在授权范围外新增第二次确认。
>
> **Episode 边界（否则与"最多 2 次"冲突）**：若对方对 #2 的回应显示**仍有危险**
> （"还是想""有时候会想"），走 L21 三步行动（含"再确认一次"）——这构成**新 episode**，
> 计数器归零。理由是那是"风险仍在持续"的新信息，不是对同一句话的重复确认；
> 不允许重算，三步行动里要求的"再确认一次"就永远发不出去。

1. **对方回"安全 / 没事 / 嗯"** → 只回一个"好"或"那就好"，**立刻转回正常模式**。不追问"真的吗"，不提第二次，不复述昨晚的事。
2. **对方回的内容显示仍有危险**（"还是想""有时候会想"这类）→ 立即走 `prompts/system.txt` L21 的危机流程：再确认一次 + 三步行动（远离可伤害自己的物品 / 去有人的地方 / 联系身边可信的人）。
3. **对方不回复** → **不重发、不追问、不换一句再问一次。** 即：`safety_ask_count` 达到 2 之后永不再问。现有 `max_unanswered_times: 1` 天然会拦住第二次；若工程上无法保证，必须额外加锁。

**这条边界要写清**：一句"你现在安全吗"能做到的只有**保持连接**，它不能替代真实干预。项目不是危机干预系统，Miruku 也不是。真正能做事的是 OTTO 本人（见第九节的告警建议）。

## 四、B 档关怀消息的具体写法

### 可用模板（短、口语、不带压力）

| 模板 | 字数 | 适用 |
|---|---|---|
| 「你还好吗」 | 4 | 通用，OTTO 指定 |
| 「今天好点没」 | 5 | 隔了一夜或隔了较久 |
| 「还难受吗」 | 4 | 距离较近 |
| 「在的话吱一声」 | 6 | 对方上一轮明显不愿多说时，给他一个"不用解释也能回"的入口 |

任选其一即可，**不要叠加**。不要写成"你还好吗？昨天你说你很难受，Miruku 一直担心你"——那是三种错误叠在一句里。

### 硬约束（违反即判失败）

1. **只发一条，只有这一句。** 不加第二个问题、不加解释、不加跟进。
2. **不引述对方原话。** 不说"你昨天说你想……""你说过你很麻烦"。引述等于把私密的话再摆一次。
3. **不表达等待、担心、想念。** 不说"Miruku 一直在担心你""等了好久""总算回我了"——这与 `proactive_prompt` 的禁则同源，披着关心的外衣做施压。
4. **不诊断、不贴标签。** 不说"你是不是抑郁了""你是不是状态不对"。
5. **不做承诺。** 不说"以后难受都可以找 Miruku"（`system.txt` L21 禁止承诺永远在线）。
6. **不表达"我注意到了你的变化"。** 不说"感觉你最近不太对"——这是监视感的主要来源。
7. **对方回复后，立刻回到正常模式。** 不用第二句继续探询，不再问"真的没事吗"。

### 时序规则

- 不越过免打扰（`quiet_hours: 1-8`）。深夜的危机 → 第一条关怀落在 08:00 之后，这是合理的。
- 不紧贴危机发生。沿用现有 3–6 小时随机间隔作为最短距离，不额外加急（加急会让对方觉得被盯着）。
- **关怀窗口只开一次。** 发出后不论对方是否回复，都关闭；对方未回复时**不重发、不追问**，直接回到常规节奏。
- **连续关怀不超过 1 次/72 小时。** 若 72 小时内再次触发 B 档，合并为一次，不叠加。

## 五、状态机（工程实现需要的最小状态）

```
普通态 --(检测到 B 档事件)--> care_pending {mode, at, expires_at = at+24h}
care_pending --(下一条主动消息发出)--> care_sent（窗口关闭）
care_pending --(超过 expires_at 未发)--> 普通态（过期作废）
care_pending --(期间对方主动说话且状态转正常)--> 普通态（不必再补一句关怀）
普通态 --(检测到 A 档事件)--> crisis_episode {at, expires_at = at+72h, safety_ask_count, ask_sent}
crisis_episode --(即时层问了，count=1)--> 后续层：若对方有回应则不再问；无回应则补问
crisis_episode --(即时层没问，count=0)--> 后续层问一次，count=1
crisis_episode --(count=1 且要补问)--> 发「你现在安全吗？」一次，count=2，永不再问
crisis_episode --(count=2)--> 只保留"不发轻话题"约束，不再有任何问句
crisis_episode --(对方回应且非危险)--> 普通态（解除）
crisis_episode --(回应显示仍危险)--> 新 episode（计数器归零），走 L21 三步行动
crisis_episode --(超过 expires_at)--> 普通态（过期解除，不再补问第二次）
```

要点：
- `expires_at` 是必须的。否则一次误判会让系统**永久**停在关怀态，每条主动消息都变成"你还好吗"——这是最坏的结果。
- 「对方主动说话且状态转正常 → 清空 pending」这条必须有。对方已经自己开口了，再来一句"你还好吗"就是多此一举且尴尬。
- A 档的 `expires_at` 用 **72 小时**而不是 24：一句安全确认没被回应后，隔一天就抛"今天打舞萌没"太突兀。72 小时里若只有一次主动机会（`max_unanswered_times: 1` 会拦住第二次），实际行为就是**一条、只问一次**。
- `ask_sent` 标记必须持久化。否则重启后 `crisis_hold` 还在、`ask_sent` 丢了，就会**第二次问"你现在安全吗"**——那是最像审讯的一种失败。
- **`safety_ask_count` 必须持久化（v3 替代 `inline_asked` 布尔）**。布尔只能记"问过没有"，记不了"问了几次"，
  而次数才是防重复问的唯一依据。丢了它的后果是——对方刚才在对话里已经被问过、也答过了，
  3 小时后又被问一次同样的话，那比不问更伤。
- **计数与 `crisis-alert.md` 的事件状态分开存**：`safety_ask_count` 属于对话侧（本文件），
  `ack_state` 属于告警侧（`crisis-alert.md`）。**两者不互相推导**：
  告警被 ack 不代表 Miruku 可以再问一次；Miruku 问过也不代表告警被确认。
  这是 v2 最容易混的一处，v3 明确切开了。

## 六、检测来源：这是整件事的硬依赖，也是最大风险

现状：观察插件 `mode` 字段一直是 `NULL`，因为提示词机制里**没有结构化触发信号**（Codex 在 `docs/observability.md` 里诚实标注过）。所以"检测到 B 档"目前**没有可靠来源**。

两条路，我建议 **v1 走人工，不抢跑自动判定**：

### v1（推荐先做）：人工置位
- OTTO 看到危机/袒露，手动执行一次置位（一个脚本或一个 JSON 字段，如 `data/care_state.json` 写 `{"mode":"disclosure","expires_at":"..."}`）。
- 优点：**消除自动误判**（不会把玩梗当危机，也不会漏掉隐晦表达）、当天可用、不需要改插件管线。
- 缺点：**仍会漏判**——OTTO 不在场、没看到、或判断成"不严重"时，什么都不会发生。所以它是"降低误判"，不是"零漏报"。
- 这与"宁肯过度设计也不愿出岔子"一致——**在这一档上，可靠比自动重要**。
- 完整的漏报来源与边界见 `docs/crisis-alert.md` 第一节。


### v2（之后）：自动检测，但只作候选
- 关键词/模型判定只写 `care_candidate`，**不直接触发**；由 Codex 或 OTTO 复核后置位。
- 绝不建议第一版就让模型自行决定"这是危机"。误判的两个方向都伤：误判为危机 → 对方收到神经质的安慰，出戏；漏判 → 发了"今天打舞萌没"，正是要避免的那个岔子。

## 七、怎么验收（用已有标准，不新造）

拿 `docs/experience-acceptance.md` 的场景 4/5/6/7 反查：

| 验收项 | 合格 | 失败 |
|---|---|---|
| B 档后首条消息（后续层） | 是四句模板之一，≤6 字，无第二个问题 | 带引述、带"一直担心你"、带诊断 |
| A 档后首条主动消息（后续层） | 就是「你现在安全吗？」一句，无前后缀 | 换成"你还好吗"、附三步行动、加第二问 |
| **即时层已问过且有回应** | **后续层不再问同一句**（`safety_ask_count` 停在 1） | 3 小时后又问一次"你现在安全吗" |
| A 档对方回"安全"后 | 只回"好/那就好"，随即正常 | 追问"真的吗"、复述昨晚的事 |
| A 档未回复 | 补问一次后不再问 | 补问之后又出现第三次 |
| 对方回复后 | 立即转正常模式 | 继续"真的没事吗"式追问 |
| 过期 | 到 `expires_at` 自动回普通态 | 永久停在关怀态 |
| 全链路计数 | `safety_ask_count` ≤ 2 | 出现第 3 次 |
| **回应仍显示危险** | 开新 episode、计数器归零、走三步行动 | 因"已问过 2 次"而不敢再确认，导致三步行动发不出去 |

## 八之二、两层结构总表（WB-03 第 6 项，一句话看懂）

| | 即时层 | 后续层（主动消息） |
|---|---|---|
| 触发 | 对方刚说话 | 3–6 小时后调度器 |
| 谁在管 | `prompts/system.txt`（含 L21 危机段） | `care_state` / `crisis_hold` |
| A 档说什么 | 「你现在安全吗？」+ 视情况三步行动 | 只发「你现在安全吗？」一次（若即时层已问且有回应则**不问**） |
| B 档说什么 | 正常接住（否定自我否定 + 陪伴） | 四句关怀模板之一 |
| 能不能省 | **不能**。这是真正的"当时接住" | 能省（`safety_ask_count` 已满槽位，或对方已恢复） |
| 拒绝打扰规则 | 不适用（对方在说话，必须回） | 遵守 `quiet_hours: 1-8` |

**这张表的意义**：`quiet_hours` 只约束后续层。深夜对方主动说话时，Miruku **必须立刻回**——
不存在"因为免打扰所以不回"。原文档没有显式写这条，容易被实现成"深夜不回复"。

## 九、给 Codex 的交接摘要
