# 聊天自然度接手核查（2026-11-07）

上午的 `data/tone_score.py` 有用：可量化长度、标点及部分出戏表达，自检 7/7 通过。但本地没有可证明属于人格 v2 上线后的对话样本，不能判断 v2 是否改善自然度，也不应马上叠加 113 字精简规则。

## 证据与限制

- `WORK_LOG.md` 记录 v2 于 09:2x 上线，DB 回读 4306 字、7 条部署探针命中。这证明规则已部署，不证明真人体验改善。
- `.tmp-tone/turns_export.json` 修改于 08:42，含 3 个会话，分别 359/143/10 个可评分 bot 回合，早于 v2。`docs/tone-baseline-20261107.md` 的 76 分、句号率 7%、短句占比 47% 是旧版基线。
- `data/chat_content.sqlite3` 最晚消息为 2026-10-20；`.stage/data_v4.db` 修改于 2026-10-26，均不能用于 v2 效果判断。
- `tone_score.py` 的 `collect()` 先按导出文件的会话顺序拼接，再用 `rows[-recent:]` 截取。导出回合只有 `role/texts/proactive_prompt`，没有时间戳。故 `--recent 100` 不能证明是跨会话按时间排列的最新 100 回合。后续导出应带时间戳和版本切点；保留旧基线口径，不擅自重算旧分数。
- 评分工具不能判断接话是否贴合、情绪是否被接住、用户是否感到打扰。人工配对样例与收件端反馈仍需单独核查。

## 其余三项

**随机忽略**：`docs/experience-acceptance.md` 记载 `astrbot_humanlike` 曾以 10% 概率静默忽略。当前仓库无运行配置或插件源码副本，今天线上是否仍开启、袒露/危机是否豁免均未核实。先核对配置与拦截顺序，再决定修改；旧文档不能当运行态事实。

**主动消息**：2026-11-06 的补丁把未回复计数按天重置。当日达上限会停发，次日允许恢复。这解决永久停发，但用户持续不回复时可能隔天再次收到消息。需看收件端实际时间线与反馈，尤其每日重置后的数量和连续天数，再决定是否跨天降频。回复率不能单独归因于内容或时机。

**高频出戏表达**：旧版基线人工复核 18 次/512 回合，其中逐张描述图片 11 次、猜测动机 5 次。它们是新样本抽查线索，不能断言 v2 仍有相同问题。评分器关键词命中只用于筛选，须人工看上下文；每轮只修一类。

## 继续工作的最小证据

1. 从线上导出 09:2x 上线之后的机器人回合，保留逐回合时间戳、匿名会话标识、主动/被动标记；正文只在本地安全位置审阅，不进仓库。
2. 至少 50 个 v2 后回合，使用相同评分口径，分别报告整体与真实用户会话，不把测试号混作用户体验。
3. 人工审阅约 20 组新旧相近场景，检查是否接住问题或情绪、短句是否生硬、是否追问或猜动机。报告只留脱敏摘要。
4. 核对线上随机忽略配置与拦截顺序，以及主动消息的实际收件端时间线，再决定第 2、3、4 项的最小修改。
