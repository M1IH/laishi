## 2. 核查随机忽略造成的沉默

查清 10% 随机忽略当前是否仍生效、实际作用于哪些消息。重点检查明确提问、情绪袒露、连续发言和普通闲聊，结合真实样例判断用户会不会把沉默理解为冷淡或故障。先提出允许沉默与必须回应的场景规则，再决定是否改代码或配置。验证重要场景不被随机忽略，同时保留日常聊天的自然节奏。一次只调整这一机制。

## 3. 核查主动消息体验

分别检查发送时机、内容重复、未回复后继续发送、断线恢复后的第一条。结合 `docs/chat-metrics-20261102.md` 的指标、主动任务记录和收件端实际气泡，定位影响最大的一种问题后才提出最小改动。系统记录或平台接受不等于用户收到；结论标明证据层级。验证收件端的时间、数量和内容符合预期。

## 4. 修复高频出戏表达

依据真实反馈与 `docs/tone-baseline-20261107.md` 的问题片段，按频率和伤害选择一类（如逐张描述表情包、猜测动机、连续追问）。每轮只修一类，保留改前改后样例供 OTTO 判断，检查没有把口吻改成固定模板。需要用户反馈时可参考 `docs/user-survey-20261025.md`，由 OTTO 决定是否发送；不要在仓库存放答卷正文。

## 每项交付格式

1. 现状与证据：版本、时间窗、样本量、实际聊天片段的脱敏摘要。
2. 结论：用户可能感到什么，证据能证明什么、不能证明什么。
3. 最小方案：涉及文件、预期收益、可能副作用与回退办法。
4. 验证：离线检查、线上生效回读、真人体验分别列出；未完成的明确标注。

人格编辑以仓库 `prompts/system.txt` 为源，通过既有 `server/deploy-persona.py` 流程部署并回读 DB；如在 WebUI 编辑，立即同步回仓库，避免再次分叉。第 1 项只读，不进入部署。
