# SnowLuma 能否解决「QQ 频繁掉线」——只读评估

> 评估人：DeepSeek　2026-10-26　提出人：OTTO
> 对象：<https://github.com/SnowLuma/SnowLuma>（v2.2.0，2026-10-24 发布）
> 边界：**只做只读调查与判断，未下载、未安装、未改任何运行配置、未碰 NapCat 副本、未发 QQ。**
> 结论写在最前面：**它能换掉 NapCat，但大概率治不好你现在这个掉线——因为掉线的主要嫌疑不在 NapCat。**

## 一、先纠正一个前提：你的日志里没有「频繁掉线」的证据

我把 `logs/astrbot-*.log` 全量统计了一遍（「适配器已连接」每出现一次 = 一次建立连接）：

| 日期 | AstrBot 启动 | 适配器加载 | 连接成功 | QQ 事件数 |
| --- | --- | --- | --- | --- |
| 10-20 | 2 | 2 | **8** | 有 |
| 10-21 | 3 | 3 | **0** | 0 |
| 10-22 | 4 | 4 | **0** | 0 |
| 10-23 | 3 | 3 | **0** | 0 |
| 10-24 | 4 | 4 | 2 | 有 |
| 10-25 | 1 | 1 | 1 | 有 |
| 10-26 | 1 | 1 | 1 | 有 |

**读法**：

- **10-20 那天确实「频繁重连」**：12:15–12:20 连了 4 次（间隔 64 秒、145 秒、69 秒），16:10–17:27 又连了 4 次。这是真掉线。
- **10-21/22/23 三天，连接次数 0、QQ 事件 0** —— 不是掉线，是**那三天 NapCat 根本没连上**（当时正在排查启动命令截断 / `QQNT.dll` 崩溃，见 `docs/napcat-manual-login.md`）。
- **10-24 起恢复**：每天 1–2 次，且都是 AstrBot 重启后的首次连接，**不是运行中掉线**。

**所以**：「频繁掉线」如果指 10-20 那种，确实发生过；但最近三天（10-24 之后）日志显示稳定。**需要 OTTO 确认「掉线」具体是什么现象**——是 QQ 客户端弹「已在其他设备登录」？是机器人不回复？还是 NapCat 进程消失？三者根因完全不同。

> **继续往下读之前**：§4.4 有一个新发现——这条链路是 **NapCat 主动连 AstrBot**（每 1 秒心跳、每 1 秒重连）。所以「日志里反复出现适配器已连接」**可能是 WS 在抖，不是 QQ 被踢**。两种情况的修法完全不同。

## 二、我发现了一个更可疑的根因：两套 QQ 同版本冲突

这是本次调查最有价值的发现，与 SnowLuma 无关，但可能直接决定换不换框架。

### 2.1 现在机器上同时跑着两个 QQ，版本还不一样

| 进程 | 可执行文件 | 实际版本 | 用途 |
| --- | --- | --- | --- |
| PID 18892（+8 子进程） | `D:\QQ\QQ.exe` | **9.9.26-44725**（启动器日志实测；exe 文件版本 9.9.20.37625） | OTTO 自己日常用的 QQ |
| PID 15740（+3 子进程） | `C:\Users\OTTO\NapCatShell-Recovery\QQ.exe` | **9.9.33-52230** | 机器人（NapCat 注入这个） |

两个根进程**同时存在、同时在跑**（启动时间相差 4 分钟）。

### 2.2 它们共用同一份 Electron profile

- 两个实例的子进程 `--user-data-dir` **都指向** `C:\Users\OTTO\AppData\Roaming\QQ`（同一个目录，逐进程核对过）。
- 该目录最后写入 `2026-10-26 08:33:44`，说明两套都在往里写。
- NapCat 的 `napcat.bat` / `napcat.quick.bat` **没有**指定独立 `--user-data-dir`，所以它接管的是默认 profile。

### 2.3 为什么这会导致掉线

同一份 QQ profile 被两个**不同版本**的 NTQQ 同时写入，典型后果：

1. **登录态互相覆盖**：`auth/`、`Network/` 下的 cookie 与会话文件被一方刷新，另一方读到旧值 → 被服务端判为「已在别处登录」而踢下线。
2. **本地数据库锁争用**：`nt_qq_*` 的消息库是单写者模型，两进程抢锁会有一方让路，表现为「消息收不到」而非进程退出。
3. **版本不一致放大问题**：9.9.26 与 9.9.33 的 profile schema 不同，互写更容易损坏状态。

**这与「换 SnowLuma 还是留 NapCat」无关** —— SnowLuma 同样是注入 `QQ.exe`、同样依赖登录态，**如果换完还让两套 QQ 共用一份 profile，掉线照旧**。

### 2.4 这一点我还没法完全证实

缺少的关键证据：**10-20 那 8 次重连发生时，`D:\QQ` 是否正在运行**。日志里没有记录这一点，当时的进程现场也已消失。所以这是**高可能性的嫌疑**，不是已证实结论。

**建议的第一步验证**（不花任何成本）：下次 OTTO 用自己的 QQ 登电脑时，观察机器人是否同时掉线。如果「开日常 QQ → 机器人掉线」稳定复现，根因就锁定了。

## 三、SnowLuma 是什么（基于官方文档与 README）

### 3.1 定位

面向 **NTQQ 桌面客户端**的**远程协议框架**，把 QQ 桥接成 **OneBot v11**：

> 一个 native addon 通过 **ptrace 级注入**把 hook 打进正在运行的 QQ 进程（Windows `QQ.exe`），解析其内部数据包，再以 OneBot v11 形式通过 HTTP / WebSocket / 反向 WS / HTTP 上报暴露出来。

**架构上与 NapCat 是同一类东西**：都是注入 QQ 客户端 + 转 OneBot v11。差别在于实现路线与配套（SnowLuma 自带 WebUI、SDK、MCP）。

### 3.2 与 NapCat 的关键对比

| 项 | NapCat（现在用的） | SnowLuma v2.2.0 |
| --- | --- | --- |
| 注入方式 | NapCatWinBootHook.dll + 启动器 | native addon，ptrace 级注入 |
| 协议 | OneBot v11 | OneBot v11 |
| 与 AstrBot 对接 | `aiocqhttp` 适配器，WS 6199 | 同样 WS（默认 3001）→ **AstrBot 侧几乎不用改** |
| Windows 支持 | 有（Shell 版） | **v2.2.0 起正式支持 win-x64**（此前只有 Linux） |
| 登录方式 | 扫码 | **只支持扫码** |
| QQ 版本敏感度 | 高（要匹配 QQ 版本） | **同样高**，官方明说「native hook 是按 QQ 版本对齐的，QQ 升级可能导致 hook 加载失败」 |
| 许可 | 开源 | **源码可见但非 OSI 开源**：非商业自托管可，商用/公开分发需书面授权 |
| 成熟度 | 成熟，社区大 | **官方自称「仍处于早期开发阶段」**，接口与配置结构可能变 |
| 掉线改善 | — | **官方文档没有任何「防掉线 / 自动重连」承诺** |

### 3.3 一个必须知道的许可限制

> SnowLuma 使用**源码可见非商业许可**，不是 OSI 开源许可。商业使用，以及公开发布修改版或衍生版，均需事先取得书面授权。随附的原生附加组件为**专有组件**。

## 四、结论：能不能解决掉线

### 4.1 直接回答

**大概率不能**，三个理由：

1. **掉线的头号嫌疑是「两套 QQ 共用一份 profile」，不是 NapCat**。换框架不改这一点，问题原样保留。
2. **SnowLuma 与 NapCat 是同一架构**（注入 QQ + OneBot）。NapCat 会掉的场景，SnowLuma 同样会掉——它们共享「依赖 QQ 客户端登录态」这个根本弱点。
3. **SnowLuma 的官方文档里没有任何防掉线/保活机制**；反而多了两条新风险：QQ 版本升级导致 hook 失效、项目早期不稳定。

### 4.2 什么情况下值得换

| 情形 | 建议 |
| --- | --- |
| 只是想要 WebUI / MCP / SDK 这些配套 | 可以试，但那不是解决掉线 |
| NapCat 在你这个 QQ 版本上确实有已知 bug | 值得对比试 |
| 想彻底摆脱「注入客户端」这条路线 | SnowLuma 帮不了，得看协议端方案（Lagrange 一类），但那是另一码事 |
| 现在这个掉线 | **先按 §二 验 profile 冲突**，再谈换框架 |

### 4.3 我的建议顺序

1. **先做零成本验证**（§2.4）：确认「开日常 QQ 是否导致机器人掉线」。这一步不用装任何东西。
2. **如果证实**：给 NapCat 副本配独立 `--user-data-dir`，或干脆把日常 QQ 与机器人 QQ 分到不同 Windows 用户/不同机器。**这比换框架省事得多**。
3. **如果没证实、且 NapCat 确实不稳**：再考虑 SnowLuma，按 §五 的隔离方式试。

## 4.4 补充：连接方向与心跳也是掉线因素（新发现）

读了 NapCat 的实际配置 `onebot11_376****47.json`（token 已脱敏）：

```json
"websocketClients": [{
  "name": "AstrBot",
  "url": "ws://127.0.0.1:6199/ws",
  "heartInterval": 1000,        // 1 秒一次心跳
  "reconnectInterval": 1000,    // 1 秒重连间隔
  "token": ""
}]
```

三个观察：

1. **是「NapCat 主动连 AstrBot」**（websocketClient 模式，NapCat 做客户端连 6199 端口，而 AstrBot 是服务端 —— 这与 §2.1 里 6199 的监听者是 python 进程吻合）。
   → **这条链路断了，NapCat 会每秒重连一次**，日志里就会看到「适配器已连接」反复出现。**10-20 那 8 次很可能就是这条 WS 在反复重连，而不是 QQ 被踢下线。**
2. **心跳 1 秒 / 重连 1 秒都偏激进**：1000ms 心跳在本地环回上没问题，但一旦 AstrBot 侧有 GC 停顿或事件循环阻塞（日志里确实配了 `Event loop watchdog: timeout=30s`），1 秒超时容易误判断线并触发重连风暴。
3. **`token` 为空**：本地环回、无鉴权，可接受，但不建议把 6199 暴露到局域网以外。

**这一条改变了优先级判断**：在确认「QQ 有没有被踢」之前，先分清是**QQ 登录态掉了**还是**AstrBot↔NapCat 的 WebSocket 掉了**——后者换 SnowLuma 也可能重演（它是同一套 OneBot WS 机制）。

**验证方法**（零成本）：下次掉线时同时看两处——

- QQ 手机端是否提示「电脑端已下线」→ 是则**登录态掉了**（§二 的 profile 冲突）；
- 只看到日志反复「适配器已连接」而 QQ 端无提示 → **WS 链路在抖**（心跳/重连参数问题）。

## 五、如果真要试 SnowLuma（供参考，未执行）

**必须遵守的隔离原则**（否则会破坏现有的手工登录副本，违反 `docs/napcat-manual-login.md` 的保护规则）：

1. **不碰 `C:\Users\OTTO\NapCatShell-Recovery`**——那是唯一可用的手工恢复入口，有 `.manual-login-reserved` 标记保护。
2. **不复用现有 profile**：给 SnowLuma 准备独立的 QQ 数据目录，避免再一次「两套共用一份 profile」。
3. **端口不要撞**：AstrBot 现在连 6199；SnowLuma 默认 3000/3001/5099，需在 AstrBot 侧新建一个 aiocqhttp 适配器指向 3001（**不要改现有适配器**，保留回退能力）。
4. **先只读验证**：能扫码登录、能收发一条测试消息、AstrBot 侧能收到事件，再谈替换。
5. **许可自查**：自用可，商用/公开分发需授权。
6. **QQ 版本要对齐**：SnowLuma 的 hook 按 QQ 版本对齐，QQ 自动升级后可能失效——比 NapCat 更需要锁版本。
